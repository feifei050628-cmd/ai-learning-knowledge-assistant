============================================================
三、今天解决的核心问题
============================================================

原来的知识库构建需要手动执行两个主要程序：

python -m rag_project.note_importer

python -m rag_project.knowledge_base_builder

第一个程序负责：

- 发现学习笔记。
- 读取基础资料和笔记。
- 规范化文本。
- 生成文本块。
- 写入 expanded_chunk_preview.json。

第二个程序负责：

- 读取切块预览。
- 加载检索模型。
- 为全部文本块生成向量。
- 保存知识库元数据。
- 保存向量矩阵。

如果只运行第一个程序，切块预览会更新，
但检索系统使用的正式元数据和向量不会更新。

如果只运行第二个程序，却没有先刷新预览，
构建程序仍然可能使用旧切块。

Day 29 用一个入口固定执行顺序，降低了漏步骤的风险。


============================================================
四、统一知识库更新入口
============================================================

新增文件：

rag_project/update_knowledge_base.py

它负责协调三个阶段：

第一步：扫描并导入最新学习笔记。

第二步：判断是否需要重新生成向量。

第三步：验证知识库输出是否一致。

主流程的结构是：

def main() -> None:
    print("第一步：扫描并导入最新学习笔记")
    import_learning_notes()

    if knowledge_base_is_current():
        print("\n知识库内容没有变化，跳过向量重建")
        verify_knowledge_base()
        print("\n知识库已经是最新状态")
        return

    print("\n第二步：检测到资料变化，重建向量知识库")
    build_knowledge_base()

    print("\n第三步：验证知识库")
    verify_knowledge_base()

    print("\n知识库更新完成")

这个流程的关键不是单纯把多个函数放在一起，
而是明确了更新顺序和提前返回条件。


============================================================
五、什么是幂等更新
============================================================

幂等可以理解为：

在输入没有变化时，重复执行同一个操作，最终状态不会发生变化。

在本项目中：

- 第一次加入新笔记后运行更新程序，会重建知识库。
- 第二次没有修改任何资料时再次运行，会直接跳过向量重建。
- 无论重复运行多少次，知识库内容保持一致。

幂等更新的价值：

- 减少不必要的模型计算。
- 缩短 API 启动时间。
- 降低重复写文件的次数。
- 让自动化脚本可以安全地反复执行。
- 使用者不需要先手动判断资料是否变化。

本项目使用内容比较实现幂等判断，
不是简单依赖文件修改时间。


============================================================
六、为什么不只比较文件数量
============================================================

只比较学习笔记数量是不可靠的。

例如：

- 笔记数量没有变化，但某篇笔记内容被修改。
- 文件名没有变化，但错误内容被修正。
- 基础资料发生变化，但学习笔记数量保持不变。
- 切块规则变化，导致文本块边界发生改变。

因此，判断知识库是否最新不能只看：

- 文件数量。
- 文档数量。
- 文件名。
- 修改日期。

Day 29 直接比较最新预览中的 chunks
与正式知识库元数据中的 chunks。

只要文本、来源、标题、chunk_id 或其他切块字段发生变化，
两个列表就不再相等，从而触发重建。


============================================================
七、知识库最新状态的判断条件
============================================================

knowledge_base_is_current() 会依次检查多个条件。

第一层：必要文件是否存在。

required_paths = [
    EXPANDED_CHUNK_PREVIEW_PATH,
    EXPANDED_METADATA_PATH,
    EXPANDED_EMBEDDINGS_PATH,
]

if not all(path.exists() for path in required_paths):
    return False

如果预览、元数据或向量文件中任何一个不存在，
知识库都不能被视为完整，必须重新构建。

第二层：检索模型是否一致。

if metadata.get("model_id") != RETRIEVAL_MODEL_ID:
    return False

同一段文本经过不同向量模型得到的向量空间不同。

如果配置中的检索模型已经变化，
旧向量不能继续与新模型生成的查询向量直接比较。

因此模型变化必须触发全部向量重建。

第三层：切块内容是否一致。

if preview.get("chunks") != metadata.get("chunks"):
    return False

这是资料变化检测的核心。

第四层：向量矩阵是否为二维 Tensor。

if embeddings.ndim != 2:
    return False

本项目的向量矩阵结构应该是：

(文本块数量, 向量维度)

第五层：向量行数是否等于文本块数量。

if embeddings.shape[0] != preview.get("chunk_count"):
    return False

一行向量必须对应一个文本块。

第六层：向量维度是否与元数据一致。

if embeddings.shape[1] != metadata.get(
    "embedding_dimension"
):
    return False

只有这些条件全部满足，函数才返回 True。


============================================================
八、为什么查询向量和知识库向量必须来自同一个模型
============================================================

语义检索会比较：

用户问题向量

与

知识库文本块向量

如果两者由不同的向量模型生成，
即使形状恰好相同，也不代表坐标含义相同。

这种情况下计算余弦相似度没有可靠意义。

所以元数据中保存 model_id，
更新检查时再与当前 RETRIEVAL_MODEL_ID 比较，
是保证检索正确性的必要条件。


============================================================
九、为什么文本块数量必须等于向量行数
============================================================

知识库中存在一个一一对应关系：

chunks[0] 对应 embeddings[0]

chunks[1] 对应 embeddings[1]

chunks[n] 对应 embeddings[n]

检索过程先在向量矩阵中找到最高分的行，
再使用相同行号读取文本块及其标题、来源等元数据。

如果文本块数量与向量行数不同，可能造成：

- 返回错误文本。
- 排名与内容错位。
- 数组越界。
- 引用错误来源。
- 检索结果无法解释。

因此更新结束后仍然要运行 verify_knowledge_base()。


============================================================
十、失败时为什么返回需要重建
============================================================

knowledge_base_is_current() 捕获了：

- FileNotFoundError
- KeyError
- ValueError
- RuntimeError
- json.JSONDecodeError

这些异常可能说明：

- 文件不存在。
- JSON 字段缺失。
- JSON 内容损坏。
- Tensor 文件无法读取。
- 数据形状不符合要求。

对于“是否可以安全复用旧知识库”这个判断，
只要无法证明旧知识库有效，就应该返回 False。

这样主流程会尝试重新构建，
而不是继续加载一个可能不一致的索引。

这种处理方式属于安全失败：

验证失败
→ 不信任旧结果
→ 进入重建流程

============================================================
十四、FastAPI lifespan 的作用
============================================================

FastAPI 的 lifespan 用于管理应用生命周期。

它可以把逻辑分成：

- 服务启动前执行的代码。
- 服务正常运行期间。
- 服务关闭时执行的代码。

Day 29 将知识库更新放进 API 的 lifespan：

@asynccontextmanager
async def lifespan(app: FastAPI):
    print("正在检查知识库是否需要更新……")
    update_knowledge_base()

    print("\n正在加载 RAG Pipeline，请稍候……")
    app.state.pipeline = RAGPipeline()
    print("RAG Pipeline 加载完成")

    yield

    app.state.pipeline = None
    print("RAG Pipeline 已释放")

yield 之前是启动阶段。

yield 所在位置代表服务运行阶段。

yield 之后是关闭阶段。


============================================================
十五、为什么必须先更新知识库，再加载 Pipeline
============================================================

RAGPipeline 初始化时会把下面的数据读入内存：

- 知识库元数据。
- 文本块列表。
- 向量矩阵。
- 检索模型。
- 生成模型。

如果顺序是：

先加载 Pipeline
→ 再更新磁盘文件

那么磁盘上的知识库虽然已经更新，
但 Pipeline 内存中仍然保存旧文本块和旧向量。

正确顺序必须是：

检查并更新磁盘知识库
→ 更新完成并验证
→ 初始化 RAGPipeline
→ 对外接收请求

这样 API 从第一个请求开始就使用最新知识库。


============================================================
十六、API 启动后的自动更新行为
============================================================

启动命令：

python -m uvicorn rag_project.api:app --host 127.0.0.1 --port 8000

服务启动时会自动执行：

1. 扫描符合命名规则的学习笔记。
2. 重新生成最新切块预览。
3. 检查知识库文件是否存在。
4. 比较最新 chunks 与正式 chunks。
5. 检查检索模型和向量形状。
6. 有变化时重建向量。
7. 无变化时跳过重建。
8. 验证正式知识库。
9. 初始化 RAGPipeline。
10. 开始接收 HTTP 请求。

因此，以后生成 dayXX笔记.txt 后，
下次启动 API 就会自动发现并加入新笔记。

如果 API 已经在运行，新增笔记不会瞬间进入内存。

需要重新启动 API，
或者手动运行更新程序后再重启 API，
才能让当前 Pipeline 加载新的向量和文本块。

目前实现的是“启动时自动更新”，
不是“运行期间实时监听文件变化”。

============================================================
十八、为什么检索结果不一定优先返回最新笔记
============================================================

真实 API 验证中，排名靠前的资料主要来自 Day 23，
同时也检索到了 Day 27 的相关内容。

这不代表 Day 28 没有加入知识库。

向量检索按照语义相似度排序，
不是按照日期新旧排序。

如果 Day 23 对某个主题的表述与问题更接近，
它就可能排在 Day 28 前面。

判断最新笔记是否成功加入知识库，应该查看：

- document_count。
- learning_note_count。
- documents 中是否存在对应 source。
- chunk_count 是否发生预期变化。
- 必要时使用针对该笔记独有内容的问题验证。

不能只凭 Top-1 的日期判断更新是否成功。

============================================================
二十、monkeypatch 在测试中的作用
============================================================

update_knowledge_base.py 默认指向正式知识库路径。

测试使用 monkeypatch 临时替换模块中的路径变量：

monkeypatch.setattr(
    updater,
    "EXPANDED_CHUNK_PREVIEW_PATH",
    preview_path,
)

同样替换元数据和向量路径。

替换只在当前测试期间生效。

测试结束后 pytest 会自动恢复原值。

这是一种依赖隔离方式：

生产代码仍然使用正式路径，
测试代码使用临时路径。


============================================================
二十一、自动更新逻辑的两个关键测试
============================================================

第一个测试：

test_current_knowledge_base_skips_rebuild

它准备：

- 相同的预览 chunks。
- 相同的正式元数据 chunks。
- 正确的 model_id。
- 形状为 (2, 512) 的测试向量。

期望：

knowledge_base_is_current() 返回 True。

第二个测试：

test_changed_content_requires_rebuild

它先准备有效知识库，
然后修改预览中的一段文本。

期望：

knowledge_base_is_current() 返回 False。

这两个测试覆盖了最重要的两个分支：

- 内容没有变化，可以复用旧向量。
- 内容已经变化，必须重新生成向量。


============================================================
二十二、为什么单元测试不加载真实模型
============================================================

知识库是否最新的判断逻辑不需要真正运行 BGE 模型。

如果每个单元测试都加载真实模型并生成 978 个向量，会导致：

- 测试速度慢。
- 占用较多显存或内存。
- 测试结果依赖本地模型缓存。
- 失败时难以区分业务逻辑错误和环境问题。

因此测试直接创建一个形状正确的零 Tensor：

torch.zeros((2, 512))

这里不关心向量语义，
只需要验证文件存在、矩阵维度和行列数量判断。

真实模型能力已经由此前的集成测试和 API 请求覆盖。

精确暂存比 git add . 更安全，
特别适合包含模型产物、实验报告和临时文件的机器学习项目。

============================================================
二十九、常见故障排查
============================================================

问题一：每次启动都重新生成向量。

检查：

- expanded_chunk_preview.json 是否每次产生不同 chunks。
- 正式元数据中的 model_id 是否与配置一致。
- 向量文件是否存在并能被 torch.load 读取。
- 向量行数是否与 chunk_count 一致。
- 向量维度是否与 embedding_dimension 一致。

问题二：新增笔记后没有进入知识库。

检查：

- 文件是否放在 LEARNING_NOTES_DIR 指定目录。
- 文件名是否符合 dayXX笔记.txt。
- 编码是否为 UTF-8。
- 笔记内容是否为空。
- 更新输出中的 learning_note_count 是否增加。

问题三：磁盘知识库已更新，但 API 仍然回答旧内容。

原因通常是正在运行的 Pipeline 已经把旧数据加载到内存。

解决方法：

- 停止 Uvicorn。
- 重新启动 API。
- 确认启动日志先显示知识库更新，再显示 Pipeline 加载。

问题四：向量模型发生变化。

更新检测会发现 model_id 不一致并触发重建。

不要直接复用旧模型生成的向量文件。

问题五：正式向量文件没有出现在 Git 状态中。

这是预期行为。

.pth 文件体积较大并被 .gitignore 排除，
在新环境中需要运行知识库构建程序重新生成。


============================================================
三十、当前方案的边界
============================================================

今天实现的是适合本地项目的可靠起点。

它的边界包括：

- 更新发生在 API 启动阶段。
- 更新期间 API 尚未开始接收请求。
- 每次资料变化会重建全部向量，而不是只计算新增块。
- 运行中的服务不会实时监听文件系统。
- 多个服务进程同时启动时没有实现分布式更新锁。

对于当前 978 个文本块的本地学习项目，
全量重建逻辑简单、结果可靠、容易验证。

当知识库扩大到大量文档时，才需要进一步考虑：

- 增量向量化。
- 文档内容哈希。
- 删除与更新向量。
- 后台任务队列。
- 文件监听。
- 数据库或向量数据库事务。
- 多进程更新锁。

这些属于后续工程扩展，
不是 Day 29 必须实现的功能。

============================================================
三十三、今天真正需要掌握的知识点
============================================================

知识点一：

知识库更新不只是重新读取文件，
还必须同步更新切块、元数据和向量。

知识点二：

幂等更新让同一个命令可以安全重复执行，
内容没有变化时不重复计算向量。

知识点三：

判断向量知识库是否可复用，至少要检查：

- 必要文件。
- 切块内容。
- 检索模型。
- 向量矩阵维度。
- 文本块数量与向量行数。

知识点四：

FastAPI lifespan 适合在服务启动时加载和释放长期资源。

知识点五：

更新知识库必须发生在加载 RAGPipeline 之前，
否则内存中可能继续使用旧数据。

知识点六：

语义检索按照相似度排名，
不是按照资料日期排名。

知识点七：

自动化测试应使用临时文件和路径替换，
避免污染真实知识库或重复加载大型模型。

============================================================
二、为什么扩大知识库后必须重新评估
============================================================

向量检索并不是“资料越多，效果一定越好”。

知识库扩大以后，会发生以下变化：

1. 候选文本块数量增加。
2. 语义相似但并非真正答案的文本块增加。
3. 正确文本块可能被其他相似文本挤到更低排名。
4. 无关问题更容易偶然匹配某些文本。
5. 正例和负例的最高相似度分布会变化。
6. 旧门槛可能变得过低或过高。
7. 原来的 Top-K 可能不再合适。

因此，每次发生以下变化后，都应该重新评估：

- 新增大量文档。
- 改变切块大小。
- 改变 overlap。
- 更换向量模型。
- 改变向量归一化方式。
- 改变相似度算法。
- 改变检索后处理逻辑。
- 修改 Top-K。
- 修改相关性门槛。

Day 27 展示的是一个标准工程闭环：

扩大知识库
→ 使用独立数据评估
→ 分析错误
→ 校准门槛
→ 调整检索逻辑
→ 分析排名深度
→ 选择运行参数
→ 再次评估

============================================================
四、什么是评估数据泄漏
============================================================

评估数据泄漏是指：

本来只应该用于测试系统的问题、答案或标签，被提前放进了系统可以检索的知识库中。

Day 27 出现的情况是：

1. 早期学习笔记记录过旧评估题及其分析。
2. Day 25 又把这些历史学习笔记加入知识库。
3. Day 26 把它们构建成向量索引。
4. Day 27 再使用相同旧问题评估时，系统可能检索到记录该问题的学习笔记。

这相当于：

把考试题和解析放进教材
→ 再用同一套考试题测试
→ 分数看起来很好
→ 但不能证明系统能处理真正的新问题

数据泄漏会导致：

- 指标虚高。
- 门槛选择失真。
- 错误判断系统已经足够可靠。
- 无法衡量对新问题的泛化能力。

解决方法：

1. 建立一套没有进入知识库的新评估问题。
2. 不把完整评估问题写入会被重新索引的学习笔记。
3. 评估集与知识库内容分开管理。
4. 每次发现评估问题进入知识库后，更换新的留出评估集。
5. 最终项目应准备长期保密或至少不参与索引的测试集。

============================================================
六、为什么要为评估报告增加 Top-K 详细记录
============================================================

旧报告主要记录：

- 返回了哪些标题。
- 最高分是多少。
- 正确资料排在第几名。
- 是否通过门槛。

这些信息可以算指标，但不够解释错误。

Day 27 新增 build_retrieved_details()，为每个返回块记录：

- rank：排名。
- title：来源标题。
- chunk_id：文本块唯一编号。
- score：相似度。
- category：资料类型。
- day：学习笔记对应天数。
- text_preview：文本内容预览。

示意结构：

{
    "rank": 1,
    "title": "某个来源标题",
    "chunk_id": "某个文本块编号",
    "score": 0.63,
    "category": "learning_note",
    "day": 20,
    "text_preview": "文本内容的前一部分"
}

详细记录的价值：

1. 可以区分“内容正确但标题标签不匹配”。
2. 可以发现正确内容是否落在其他来源中。
3. 可以检查前几名为什么得到高分。
4. 可以识别知识库中的重复内容。
5. 可以发现错误问题被哪段笔记误吸引。
6. 可以判断问题出在向量检索、标签设计还是评估规则。
7. 报告可以用于人工错误分析，而不仅是展示一个百分比。

工程上，可解释性报告往往比单个总分更重要。


============================================================
七、为什么一个问题可以有多个正确来源
============================================================

扩展知识库中，同一个知识点可能同时出现在：

- 基础资料。
- 某一天的学习笔记。
- 后续复习笔记。
- API 实现说明。
- 测试说明。

如果评估规则只允许一个 expected_title，那么系统即使检索到了正确内容，也可能因为标题不同而被判错。

旧格式：

"expected_title": "唯一正确标题"

新格式：

"expected_titles": [
    "可接受来源一",
    "可接受来源二",
    "可接受来源三"
]

新格式的含义：

只要返回结果的 title 位于 expected_titles 列表中，就认为命中了正确来源。

对应的核心判断：

if chunk["title"] in expected_titles:
    return rank

这样可以减少“内容检索正确，但评估标签过窄”造成的假失败。


============================================================
八、正例与负例怎样表示
============================================================

Day 27 统一使用 expected_titles 列表。

正例：

expected_titles 是非空列表。

含义：

问题与知识库相关，系统应该接受，并且正确来源应该出现在返回结果中。

负例：

expected_titles 是空列表。

含义：

问题不属于知识库范围，系统应该通过相似度门槛拒绝。

Python 判断：

is_relevant = bool(expected_titles)

因为：

- bool(["某个标题"]) 为 True。
- bool([]) 为 False。

- 正例数量：9
- 负例数量：6


============================================================
九、为什么要兼容新旧评估格式
============================================================

旧报告使用 expected_title。

新报告使用 expected_titles。

如果校准程序只认识新字段，那么过去生成的报告将无法读取。

Day 27 在 calibrate_threshold.py 中增加 get_expected_titles()：

1. 如果存在 expected_titles，直接使用列表。
2. 否则读取旧字段 expected_title。
3. 旧字段有标题时，将它包装成单元素列表。
4. 旧字段为 None 时，返回空列表。
5. 如果新字段不是列表，主动抛出 ValueError。

这叫向后兼容。

向后兼容的好处：

- 新代码能读取新报告。
- 新代码也能读取历史报告。
- 数据迁移可以逐步进行。
- 不需要一次性删除所有旧文件。

============================================================
十一、阈值和 Top-K 解决的是不同问题
============================================================

min_similarity 解决：

“这个问题是否足够相关，系统应该回答还是拒绝？”

top_k 解决：

“系统最多把排名前多少个合格文本块交给后续生成阶段？”

二者的关系：

- 门槛是准入条件。
- Top-K 是候选数量上限。

门槛过低：

- 无关问题容易通过。
- 噪声文本块容易进入上下文。
- 生成模型更容易幻觉。

门槛过高：

- 正确问题可能被拒绝。
- 召回率下降。
- 系统变得过于保守。

Top-K 过小：

- 正确资料可能在更低位置而被截断。
- Hit@K 下降。

Top-K 过大：

- 返回更多重复或低质量文本。
- 生成上下文更长。
- 推理耗时和 token 成本增加。
- 错误信息可能干扰答案。


============================================================
十二、什么是混淆矩阵
============================================================

门槛判断可以看成一个二分类问题：

- 相关问题应该接受。
- 无关问题应该拒绝。

四种结果：

TP，True Positive，真正例：

问题相关，并且系统接受。

FP，False Positive，假正例：

问题无关，但系统错误接受。

TN，True Negative，真负例：

问题无关，并且系统正确拒绝。

FN，False Negative，假负例：

问题相关，但系统错误拒绝。

门槛校准的目标通常是：

- 尽量减少 FP。
- 同时不要造成太多 FN。
- 在安全性与召回率之间取得平衡。


============================================================
十三、Precision、Recall、Specificity 的含义
============================================================

Precision，精确率：

Precision = TP / (TP + FP)

含义：

所有被系统接受的问题中，有多少确实属于知识库范围。

Precision 低说明：

系统容易对无关问题也强行回答。

Recall，召回率：

Recall = TP / (TP + FN)

含义：

所有真正相关的问题中，有多少被系统接受。

Recall 低说明：

系统拒绝了太多本来可以回答的问题。

Specificity，特异度或负例识别率：

Specificity = TN / (TN + FP)

含义：

所有真正无关的问题中，有多少被正确拒绝。

在 RAG 门槛评估中：

irrelevant_rejection_rate 与 specificity 表达的是相近目标。


============================================================
十四、F1 与 Balanced Accuracy 的含义
============================================================

F1：

F1 = 2 × Precision × Recall / (Precision + Recall)

F1 同时考虑 Precision 与 Recall。

只有二者都较高时，F1 才会较高。

Balanced Accuracy：

Balanced Accuracy = (Recall + Specificity) / 2

它分别计算正例和负例表现，再取平均。

为什么有用：

当正负样本数量不均衡时，普通 Accuracy 可能被样本较多的一类主导。

Balanced Accuracy 能避免系统只擅长其中一类，却获得看似很高的总准确率。

- Recall = 100%

完美候选门槛共有 14 个：

0.45、0.46、……、0.58

这叫完美门槛区间。

============================================================
十七、为什么选择 0.45，而不是直接选择中点 0.5151
============================================================

中点 0.5151 位于最高负例和最低正例之间，数学上很直观。

但当前项目选择 0.45，原因包括：

1. 0.45 已经高于当前最高负例分数 0.44295。
2. 0.45 在当前数据上已经实现 FP=0、FN=0。
3. 它是完美区间的下边界。
4. 相比 0.5151，它为未来表达方式不同的相关问题保留更多召回空间。
5. 改动幅度较小，便于从旧门槛 0.40 平稳升级。

工程选择不是只追求“离两边一样远”。

还要考虑：

- 误答风险。
- 漏答风险。
- 样本量是否足够。
- 未来问题分布是否会变化。
- 当前产品更偏保守还是更偏召回。


============================================================
十八、为什么校准报告 100%，最终检索正确率却不是 100%
============================================================

校准报告中的 100% 衡量的是：

门槛有没有正确区分相关问题和无关问题。

最终检索总体正确率还要求：

1. 相关问题通过门槛。
2. 正确来源进入 Top-K。
3. 无关问题没有通过门槛。

Day 27 最终结果中：

- 9 个正例全部通过门槛。
- 但只有 8 个正例的正确来源进入 Top-5。
- 6 个负例全部被门槛拒绝。

所以正确用例数量：

8 + 6 = 14

总体正确率：

14 / 15 = 93.33%

这说明：

门槛分类已经解决，但仍有一个排名或知识表达问题没有解决。


============================================================
十九、为什么要对每个返回文本块单独过滤
============================================================

旧逻辑可能只根据最高分判断整个查询是否通过：

passed = max_score >= min_similarity

如果最高分通过，就可能返回 Top-K 中所有块。

问题是：

第 1 名可能得分 0.70，达到门槛；

第 4 名或第 5 名可能只有 0.30，却仍然被放入生成上下文。

这会把低相关噪声交给生成模型。

Day 27 在 retrieval.py 的返回循环中增加：

if score < min_similarity:
    continue

现在的逻辑是：

1. 先取得相似度排名靠前的候选。
2. 再逐个检查每个候选的分数。
3. 只有达到 min_similarity 的块才进入 retrieved_chunks。

因此：

top_k 表示最多返回多少块。

它不保证一定返回这么多块。

如果只有 2 个块达到门槛，即使 top_k=5，也只返回 2 个。


============================================================
二十、查询级门槛与文本块级门槛
============================================================

查询级判断：

最高分是否达到门槛。

用途：

决定整个问题是否值得回答。

文本块级判断：

每个候选块是否达到门槛。

用途：

决定某个文本块是否有资格进入生成上下文。

二者同时存在更合理：

查询
→ 计算所有相似度
→ 取得最高分和 Top-K 候选
→ 最高分低于门槛：整个查询拒绝
→ 最高分达到门槛：继续处理
→ 每个候选块再次检查门槛
→ 只保留合格文本块

这种设计能减少“一个高分块带着多个低分块一起通过”的问题。

============================================================
二十二、为什么测试中要 monkeypatch encode_query
============================================================

真实 encode_query 需要：

- tokenizer。
- 向量模型。
- 真实模型推理。
- CPU 或 GPU 计算。

测试 retrieval.py 的过滤逻辑时，不需要验证真实模型。

因此测试使用 monkeypatch，将 encode_query 临时替换为固定函数。

固定查询向量示意：

torch.tensor([[1.0, 0.0]])

然后人工准备文本块向量，使相似度结果完全可预测。

好处：

1. 测试运行快。
2. 不依赖网络下载模型。
3. 不依赖 GPU。
4. 不受模型版本变化影响。
5. 失败时容易判断是检索逻辑问题，而不是模型问题。

这种测试叫隔离测试或单元测试。

============================================================
二十四、什么是 Hit@K
============================================================

Hit@K 用于衡量：

在相关问题中，正确来源是否出现在前 K 个结果内。

计算方式：

Hit@K = Top-K 中命中正确来源的正例数 / 正例总数

例如：

9 个正例中有 8 个在前 5 名找到正确来源：

Hit@5 = 8 / 9 = 88.89%

Hit@K 只关心有没有进入前 K 名。

如果正确来源排第 1 和排第 5，两者对 Hit@5 的贡献相同。

因此还需要 MRR 衡量排名位置。


============================================================
二十五、什么是 MRR
============================================================

MRR 全称 Mean Reciprocal Rank，平均倒数排名。

单个问题的得分：

- 正确来源排第 1：1 / 1 = 1.00
- 正确来源排第 2：1 / 2 = 0.50
- 正确来源排第 3：1 / 3 ≈ 0.333
- 正确来源排第 5：1 / 5 = 0.20
- Top-K 未命中：0

最后把所有正例的倒数排名取平均。

MRR 越高，说明正确资料平均排得越靠前。

Hit@K 高但 MRR 较低，通常表示：

虽然多数问题能找到正确资料，但正确资料经常排在第 3、第 4 或第 5，而不是第 1。

Day 27 最终：

- Hit@5：88.89%
- MRR@5：56.48%

说明召回已经较好，但首位排序质量仍有提升空间。


============================================================
二十六、为什么要单独分析排名深度
============================================================

如果只运行当前 top_k，就不知道正确资料是否存在于更深的位置。

Day 27 新建 analyze_ranking_depth.py，使用最大深度 10 做诊断。

它只分析正例，并计算：

- Hit@1
- Hit@3
- Hit@5
- Hit@10
- MRR@10

诊断结果：

- 正例数量：9
- Hit@1：33.33%
- Hit@3：77.78%
- Hit@5：88.89%
- Hit@10：100.00%
- MRR@10：58.33%

这组结果说明：

1. 只有三分之一的问题把正确来源排在第一名。
2. 前三名可以找到大多数正确来源。
3. 从 Top-3 增加到 Top-5，命中率继续提升。
4. 前十名能覆盖当前全部正例。
5. 但不能因为 Hit@10=100%，就直接把生产参数设置为 10。


============================================================
二十七、诊断 Top-K 与运行 Top-K 的区别
============================================================

诊断 Top-K：

为了分析正确资料到底排在多深的位置，可以临时设置较大的 K。

运行 Top-K：

系统真正向生成模型提供的最大文本块数量。

诊断时使用 Top-10 不等于运行时必须使用 Top-10。

诊断目标：

- 观察排名分布。
- 判断正确资料是否完全没有被模型识别。
- 选择合理候选范围。

运行目标：

- 保证足够召回。
- 控制上下文长度。
- 降低噪声。
- 控制推理成本。


============================================================
二十八、为什么最终选择 Top-K=5
============================================================

排名深度结果：

- Hit@3：77.78%
- Hit@5：88.89%
- Hit@10：100.00%

从 3 增加到 5：

- 多找回一个正例。
- 上下文增加幅度有限。
- 配合逐块 0.45 门槛，可以过滤低分候选。

从 5 增加到 10：

- 当前小样本上能达到 100% 召回。
- 但最多候选数量翻倍。
- 更容易加入重复或边缘相关内容。
- 增加生成阶段的上下文负担。
- 可能只是对 9 个正例过拟合。

因此选择 Top-K=5 是召回与噪声之间的折中。

正确理解：

Top-K=5 不是说一定返回 5 个块。

逐块门槛会让最终返回数量小于或等于 5。


============================================================
二十九、为什么不能为追求 100% 盲目增大 Top-K
============================================================

当前 Hit@10=100% 只来自 9 个正例。

样本很小时，直接为当前评估集调到 100% 容易过拟合。

过拟合表现为：

- 对这 9 个问题表现很好。
- 对新问题不一定更好。
- 参数选择过度依赖当前样本。
- 返回内容越来越多，但有效信息比例下降。

更可靠的方法：

1. 保留当前 Top-K=5。
2. 增加更多独立正例和负例。
3. 分析唯一一个 Top-5 排名未命中的原因。
4. 改善文档标题、切块或查询表达。
5. 必要时再比较 Top-K=6、7、8。
6. 同时评估生成答案质量，而不是只看召回。

三十二、检索评估与生成评估的区别
============================================================

检索评估关注：

- 是否找到正确资料。
- 正确资料排在第几名。
- 相似度是否超过门槛。
- 无关问题是否被拒绝。

典型指标：

- Hit@K。
- MRR@K。
- 相关问题接受率。
- 无关问题拒绝率。
- Precision、Recall、Specificity。

生成评估关注：

- 最终答案是否回答问题。
- 是否忠于检索上下文。
- 是否出现幻觉。
- 引用是否正确。
- 答案是否清晰完整。

检索正确不等于生成一定正确。

检索错误通常会让生成更难正确。

一个完整 RAG 项目需要同时评估两层。


============================================================
三十三、GBK UnicodeEncodeError 的原因
============================================================

排名深度分析程序最初使用了一个 Unicode 图形符号作为命中标记。

Windows PowerShell 的输出编码环境尝试使用 GBK 编码该字符时，出现：

UnicodeEncodeError

这不是检索算法错误，也不是模型加载错误。

错误发生在：

Python 准备把某个字符打印到终端时，当前输出编码无法表示该字符。

解决方法：

将图形符号替换为 ASCII 文本：

[OK]

经验：

1. 面向 Windows 终端的脚本尽量使用普通 ASCII 状态标记。
2. 文件内容可以使用 UTF-8，但终端编码仍可能不同。
3. py_compile 只检查语法，不会执行 print，因此发现不了运行时编码错误。
4. 编译通过后仍要实际运行程序。


============================================================
三十四、py_compile、pytest 和实际运行分别验证什么
============================================================

py_compile：

python -m py_compile 某个文件.py

主要验证：

- Python 语法是否正确。
- 缩进、括号、冒号等是否有明显语法错误。

不能验证：

- 函数是否按预期工作。
- 文件是否存在。
- 模型能否加载。
- 终端字符能否编码。
- 指标是否正确。

pytest：

主要验证：

- 已编写测试覆盖到的行为是否符合预期。
- 修改是否破坏已有功能。

不能自动证明：

- 没写测试的路径一定正确。
- 真实用户问题表现良好。
- 模型质量足够。

实际运行评估程序：

主要验证：

- 真实模型和知识库能否加载。
- 真实向量检索能否执行。
- 报告能否生成。
- 实际指标是多少。

三者需要配合使用。

四十一、今天必须掌握的知识点总结
============================================================

1. 知识库扩大后必须重新评估，旧参数不能直接假定继续有效。
2. 评估问题进入知识库会造成数据泄漏和虚高指标。
3. 评估集应与知识库内容分开管理。
4. 完整评估问题不应复制到会被重新索引的学习笔记。
5. 扩展知识库中一个问题可能有多个正确来源。
6. expected_titles 列表比唯一 expected_title 更适合多来源知识库。
7. expected_titles 为空列表表示负例，非空列表表示正例。
8. 向后兼容可以让新校准代码继续读取旧报告。
9. 评估报告应记录 rank、score、title、chunk_id 和内容预览。
10. 详细检索记录可以区分模型错误、标签错误和数据泄漏。
11. min_similarity 决定回答还是拒绝。
12. top_k 决定最多保留多少个候选块。
13. 门槛和 Top-K 解决的是两个不同问题。
14. TP 是相关且接受，FP 是无关但接受。
15. TN 是无关且拒绝，FN 是相关但拒绝。
16. Precision 衡量被接受问题的可靠程度。
17. Recall 衡量相关问题被接受的比例。
18. Specificity 衡量无关问题被拒绝的比例。
19. F1 同时考虑 Precision 与 Recall。
20. Balanced Accuracy 平均考虑正例召回和负例识别。
21. 当前最低正例分数约为 0.5872。
22. 当前最高负例分数约为 0.4430。
23. 当前正负例分离间隔约为 0.1443。
24. 当前完美门槛候选区间是 0.45 到 0.58。
25. 选择 0.45 可以拒绝当前负例，同时保留更多未来召回空间。
26. 校准指标 100% 不代表 Top-K 排名命中也是 100%。
27. 每个返回文本块都应该单独检查相关性门槛。
28. top_k=5 表示最多返回 5 块，不表示一定返回 5 块。
29. monkeypatch 可以隔离真实模型，专门测试检索逻辑。
30. 配置默认值应集中在 config.py，避免多处写死。
31. Hit@K 衡量正确来源有没有进入前 K 名。
32. MRR 衡量正确来源平均排得是否靠前。
33. Hit@K 高而 MRR 较低，表示正确来源经常不是第一名。
34. 诊断 Top-K 可以较大，运行 Top-K 不必与诊断深度相同。
35. 当前 Hit@1=33.33%、Hit@3=77.78%、Hit@5=88.89%、Hit@10=100%。
36. Top-K=5 是召回、噪声和成本之间的折中。
37. 不能为了小样本指标达到 100% 就盲目增大 Top-K。
38. 最终门槛为 0.45，最终 Top-K 为 5。
39. 最终 Hit@5 为 88.89%，MRR@5 为 56.48%。
40. 最终相关问题接受率和无关问题拒绝率均为 100%。
41. 最终总体正确率为 93.33%，即 15 个样本中 14 个正确。
42. 剩余错误属于排名命中问题，而不是接受/拒绝问题。
43. py_compile 通过只表示语法正确，不能发现运行时终端编码错误。
44. Windows GBK 终端可能无法打印部分 Unicode 图形字符。
45. ASCII 状态标记比特殊符号更适合跨终端脚本。
46. 15 个样本只能证明当前小型评估集表现，不能代表所有真实用户问题。
47. 检索评估不能代替生成答案质量评估。
48. 导入 Day 27 笔记后，应使用新的未见问题再次评估。


============================================================
四十二、Day 27 核心结论
============================================================

Day 27 的核心不是把两个默认数字改掉。

真正完成的是一套可解释的检索优化方法：

发现旧评估集泄漏
→ 建立新的独立正负样本
→ 允许多个正确来源
→ 记录逐块检索详情
→ 用混淆矩阵校准门槛
→ 用 Hit@K 和 MRR 分析排名
→ 为每个返回块应用门槛
→ 在召回与噪声之间选择 Top-K
→ 使用最终参数重新评估

最终参数：

- DEFAULT_TOP_K = 5
- DEFAULT_MIN_SIMILARITY = 0.45

最终结果：

- Hit@5 = 88.89%
- MRR@5 = 56.48%
- 相关问题接受率 = 100.00%
- 无关问题拒绝率 = 100.00%
- 总体正确率 = 93.33%

从工程角度看：

门槛决定系统是否应该回答。

Top-K 决定系统最多查看多少个候选。

Hit@K 衡量正确资料能否被召回。

MRR 衡量正确资料排得是否足够靠前。

逐块过滤决定哪些候选真正有资格进入生成上下文。

评估数据隔离决定这些指标是否值得相信。

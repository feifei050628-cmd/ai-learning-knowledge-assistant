============================================================
三、为什么检索正确仍然不代表回答正确
============================================================

检索层解决的是：

- 是否找到正确资料。
- 正确资料排在什么位置。
- 相似度是否超过门槛。
- 无关问题是否被拒绝。

生成层解决的是：

- 是否真正回答用户提出的问题。
- 是否覆盖资料中的关键事实。
- 是否忠于检索上下文。
- 是否遗漏重要技术名词。
- 是否引用了实际返回的资料。
- 资料不足时是否正确拒答。

即使正确资料已经进入 Top-K，生成模型仍可能：

- 忽略最相关的句子。
- 只回答部分要点。
- 输出过于笼统的总结。
- 复述提示词。
- 遗漏引用。
- 生成不存在的引用编号。
- 在资料不足时强行回答。

所以完整 RAG 项目必须分别评估检索质量和生成质量。


============================================================
四、为什么重新建立 Day 28 评估集
============================================================

知识库已经包含历史学习笔记。

如果继续使用以前已经出现过的完整测试问题，指标可能受到数据泄漏影响。

Day 28 使用新的生成评估文件：

rag_project/generation_evaluation_cases_day28.json

评估集包含：

- 5 个知识库内问题。
- 4 个知识库外问题。

正例覆盖不同类型的知识：

- 训练过程中的操作顺序。
- 多头注意力输出合并。
- Docker 镜像与容器关系。
- 检索门槛过低的风险。
- Markdown 代码块切分原则。

负例来自知识库没有覆盖的生活类主题。

本笔记不复制评估问题原文，避免以后重新导入学习笔记时把完整测试题写进知识库。


============================================================
五、生成评估样例的主要字段
============================================================

每个评估样例主要包含：

id

用例的稳定编号。

query

真正交给 RAG 系统的问题。

expected_passed

期望问题是否应该通过相关性门槛。

expected_titles

允许被判定为正确来源的标题列表。

keyword_groups

答案应覆盖的语义要点，每个要点可以允许多个同义表达。

正例：

- expected_passed 为 true。
- expected_titles 非空。
- keyword_groups 非空。

负例：

- expected_passed 为 false。
- expected_titles 为空列表。
- 不要求生成关键词覆盖。


============================================================
六、为什么 expected_titles 使用列表
============================================================

扩展知识库中，同一个主题可能同时出现在：

- 基础资料。
- 不同日期的学习笔记。
- 总结章节。
- 测试与复盘章节。

因此一个问题可能有多个合理来源。

如果只允许唯一 expected_title，会把其他正确来源错误判为失败。

Day 28 使用：

expected_titles: [标题 A, 标题 B]

评估时，只要返回来源标题存在于这个列表中，就算正确来源命中。

这是一种多标签评估设计。


============================================================
七、为什么仍然保留旧字段兼容
============================================================

旧生成评估文件使用 expected_title。

新文件使用 expected_titles。

evaluate_generation.py 新增：

get_expected_titles(case)

它的行为是：

1. 如果存在 expected_titles，直接读取列表。
2. 否则尝试读取旧的 expected_title。
3. 旧标题不为空时，把它包装成单元素列表。
4. 旧标题为空时，返回空列表。
5. 验证列表中的标题都是非空字符串。

这样新评估程序可以继续读取旧格式，降低升级成本。


============================================================
八、关键词组为什么允许同义表达
============================================================

自然语言答案没有唯一写法。

例如同一个技术动作，模型可能使用：

- 更新参数。
- 参数更新。

同一个关系可能写成：

- 镜像是容器的基础。
- 容器基于镜像创建。

如果评分器只匹配唯一字符串，会把语义正确但措辞不同的答案判错。

因此 keyword_groups 的每个元素是一组可接受表达。

只要答案命中组内任意一个表达，这个语义要点就算覆盖。

正确做法：

- 同义表达应加入同一关键词组。
- 每个组代表一个独立事实或语义要点。
- 不能为了提高分数，把真正缺失的事实删掉。
- 不能把错误答案中出现的无关词当作正确替代表达。


============================================================
九、关键词覆盖率怎样计算
============================================================

设一个正例包含 N 个关键词组。

答案命中了其中 M 组。

关键词覆盖率为：

M / N

例如：

- 3 组全部命中，覆盖率为 1.0。
- 3 组命中 2 组，覆盖率约为 0.667。
- 3 组命中 1 组，覆盖率约为 0.333。

Day 28 的用例整体通过条件要求正例覆盖率等于 1.0。

这是一条严格规则。

平均关键词覆盖率则是所有正例覆盖率的平均值。

最终平均值为：

0.8666666667

即 86.67%。


============================================================
十、关键词覆盖率的能力边界
============================================================

关键词覆盖率属于规则型代理指标。

它的优点：

- 计算简单。
- 运行稳定。
- 不需要额外模型。
- 容易定位缺失的语义要点。
- 适合做回归测试和基线对比。

它的局限：

- 命中关键词不保证句子逻辑正确。
- 未命中关键词不一定代表语义错误。
- 同义表达列表不可能穷尽所有自然语言。
- 不能判断事实是否自相矛盾。
- 不能完整评估流畅度和可读性。

因此应该把它与以下检查结合：

- 来源标题命中。
- 检索门槛判断。
- 引用有效性。
- 拒答正确性。
- 人工抽查。


============================================================
十一、Day 28 的多维生成评估
============================================================

今天没有用一个模糊的“回答正确率”覆盖所有问题。

评估程序分别计算：

1. gate_accuracy
2. source_title_hit_rate
3. average_keyword_coverage
4. citation_presence_rate
5. citation_validity_rate
6. refusal_accuracy
7. overall_case_pass_rate

每个指标对应不同故障类型。

这样可以判断问题发生在：

- 检索门槛。
- 来源召回。
- 答案内容。
- 引用格式。
- 引用范围。
- 负例拒答。


============================================================
十二、gate_accuracy 的含义
============================================================

gate_accuracy 检查：

系统的 passed 是否与 expected_passed 一致。

正例应该：

passed = true

负例应该：

passed = false

最终结果：

9 / 9 = 100%。

这说明当前 0.48 门槛在 Day 28 的 9 个样例上完成了正确接受和拒绝。

但它不等于答案内容 100% 正确。


============================================================
十三、source_title_hit_rate 的含义
============================================================

对于每个正例，评估程序检查返回 sources 中是否至少存在一个允许的标题。

只要：

source["title"] in expected_titles

就算正确来源命中。

最终结果：

5 / 5 = 100%。

这说明五个正例都检索到了可接受来源。

如果来源命中为真但答案内容不完整，问题更可能发生在生成阶段，而不是召回阶段。


============================================================
十四、引用出现率的含义
============================================================

引用出现率检查正例答案中是否出现：

【资料数字】

evaluate_generation.py 使用正则表达式提取编号：

【资料(\d+)】

如果答案中至少提取到一个编号，就认为引用出现。

最终结果：

100%。


============================================================
十五、引用有效率的含义
============================================================

引用出现不代表引用有效。

假设 API 实际返回 3 个来源。

合法编号只能是：

- 【资料1】
- 【资料2】
- 【资料3】

如果答案出现【资料4】，就是越界引用。

citations_are_valid 的核心规则是：

每个编号都满足：

1 <= number <= source_count

没有引用时也判为无效。

Day 28 最终引用有效率为 100%。


============================================================
十六、拒答准确率的含义
============================================================

负例只有同时满足以下条件才算正确拒答：

1. passed 为 false。
2. answer 去除空白后严格等于“现有资料不足”。
3. sources 为空列表。

最终结果：

4 / 4 = 100%。

这说明四个知识库外问题全部被门槛拒绝，并且没有返回误导性来源。


============================================================
十七、整体用例通过条件
============================================================

正例必须同时满足：

- 门槛判断符合预期。
- 正确来源命中。
- 关键词覆盖率等于 1.0。
- 引用编号有效。

负例必须同时满足：

- 门槛判断符合预期。
- 返回标准拒答。
- sources 为空。

最终 9 个样例中 8 个整体通过：

8 / 9 = 88.89%。


============================================================
十八、最初暴露出的引用问题
============================================================

在最初的生成评估中，检索来源能够命中，但小型生成模型没有稳定输出引用编号。

当引用完全交给模型时，可能发生：

- 忘记引用。
- 格式不一致。
- 引用不存在的编号。
- 引用编号与 sources 顺序不一致。
- 拒答时仍输出引用。

这会让 API 的答案看似有依据，实际无法验证来源。

引用可靠性问题不应该只依赖提示词解决。


============================================================
十九、职责分离：门槛决定是否回答
============================================================

最终架构中，检索层负责判断资料是否足够相关。

如果 retrieval_result["passed"] 为 false：

- 直接返回“现有资料不足”。
- passed 返回 false。
- sources 返回空列表。
- 不调用生成模型。

这有三个好处：

1. 避免模型对无关问题强行生成。
2. 减少不必要的推理开销。
3. 让拒答行为稳定、可测试。

生成模型不再负责猜测资料是否足够。


============================================================
二十、职责分离：模型只负责生成正文
============================================================

通过门槛后，生成模型负责：

- 根据已经提供的资料回答。
- 保留关键技术名词。
- 使用简洁中文。
- 避免输出思考过程。

生成模型不再负责：

- 决定是否拒答。
- 创建来源编号。
- 保证编号一定在合法范围内。

这种设计把概率性任务和确定性任务分开。


============================================================
二十一、职责分离：程序负责引用编号
============================================================

rag_pipeline.py 新增静态方法：

append_source_citations(answer, source_count)

它首先清理答案两端空白。

如果 source_count 小于等于 0，直接返回清理后的答案。

如果答案是标准拒答“现有资料不足”，不追加引用。

否则按照真实来源数量生成：

【资料1】 【资料2】 ……

再统一追加到回答末尾。

这样引用编号来自实际 sources，而不是模型的自由生成。


============================================================
二十二、为什么程序化引用比提示词引用稳定
============================================================

提示词只能告诉模型“应该怎么做”。

它不能保证模型每次都服从。

程序逻辑则可以保证：

- 编号从 1 开始。
- 编号数量与来源数量一致。
- 不会出现越界编号。
- 拒答时不会附带来源。
- 格式始终统一。

能用确定性代码保证的格式约束，不应该全部交给生成模型。


============================================================
二十三、提示词为什么简化
============================================================

当前使用的是 Qwen2.5-0.5B-Instruct。

0.5B 模型体积小、运行成本低，但复杂指令遵循能力有限。

过多职责同时写进提示词时，模型可能：

- 过度拒答。
- 忽略回答内容。
- 复述任务说明。
- 忘记引用要求。
- 输出固定模板而不是解决问题。

最终 SYSTEM_PROMPT 只保留核心生成要求：

- 使用中文。
- 已提供资料已经通过相关性检查。
- 只根据资料回答。
- 保留关键技术名词。
- 简洁、准确。
- 不输出思考过程。


============================================================
二十四、增强提示词的最终结构
============================================================

build_rag_prompt 生成的提示词包含：

【参考资料】

每个文本块包括：

- 资料编号。
- 标题。
- 正文。

【用户问题】

保存用户真正提出的问题。

【任务】

要求模型根据参考资料直接回答，并保持简洁。

提示词中的资料顺序与 API sources 中的顺序保持一致。

程序追加的【资料N】因此可以映射回相同排名的来源。


============================================================
二十五、为什么提高最低相似度门槛
============================================================

Day 27 最终使用 0.45。

Day 28 加入新的知识库外负例后，发现有一个负例最高相似度高于 0.45。

这意味着：

旧门槛对旧评估集有效，但面对新的负例不再足够安全。

新的分数分布中：

- 新负例最高分约为 0.4729。
- 正例最低分仍明显高于该值。

因此将默认门槛调整为：

DEFAULT_MIN_SIMILARITY = 0.48

0.48 能拒绝该新负例，同时保留当前正例。


============================================================
二十六、为什么新增负例后必须重新校准
============================================================

门槛不是模型的永久常数。

它依赖：

- 知识库内容。
- 文本切块方式。
- 检索模型。
- 查询分布。
- 正例与负例难度。

新增更难的负例后，最高负例分数可能上升。

新增边缘正例后，最低正例分数可能下降。

所以每次重大扩库或更换评估集后，都应该检查正负例分数分布。


============================================================
二十七、默认门槛修改影响哪些文件
============================================================

config.py：

DEFAULT_MIN_SIMILARITY 从 0.45 修改为 0.48。

tests/test_schemas.py：

请求模型默认门槛断言同步为 0.48。

tests/test_api_basic.py：

/validate 返回值中的默认门槛断言同步为 0.48。

retrieval_evaluation_report.json：

重新运行检索评估后，报告记录当前门槛为 0.48。

配置和测试必须一起更新，否则测试会继续期待旧值。


============================================================
二十八、为什么最终不追求评估集 100%
============================================================

最终仍有一个知识库内用例没有满足全部关键词组。

这个用例的实际情况是：

- 成功通过门槛。
- 命中了允许的正确来源。
- 引用编号有效。
- 但回答只覆盖了部分预期语义要点。

这说明问题主要位于小型生成模型的内容选择，而不是检索或引用系统。

继续针对这一个用例修改提示词、上下文数量或关键词规则，容易对当前 9 个样例过拟合。

因此最终保留真实失败：

- 承认系统限制。
- 保存错误样例用于以后比较。
- 不通过放宽错误标准获得虚假满分。


============================================================
二十九、如何理解最终唯一失败
============================================================

唯一失败并不表示整个 RAG 链路完全失败。

它可以被拆解为：

- Gate：正确。
- Source：正确。
- Citation：正确。
- Content coverage：不完整。

这正是多维评估的价值。

如果只看 overall_case_pass_rate，只能看到 88.89%。

拆分后可以知道下一步优化方向是：

- 更强的生成模型。
- 更好的生成上下文压缩。
- 专门的重排序器。
- 更可靠的语义评估。

而不是继续调整已经达到 100% 的拒答或引用逻辑。


============================================================
三十、无收益实验怎样处理
============================================================

开发中曾尝试过更复杂的提示词和不同的上下文选择方式。

这些实验没有稳定提高最终指标，因此没有进入最终设计。

最终代码恢复为：

context_chunks = retrieved_chunks

也就是保持检索结果原有顺序和数量。

失败实验不作为今天必须掌握的功能，也不应该为了保留“做过的工作”留在生产路径中。

工程上的正确做法是：

- 用指标验证改动。
- 没有收益就回退。
- 保留最终稳定方案。
- 不把临时实验代码提交到正式实现。


============================================================
三十一、为什么上下文并非越少越好
============================================================

生成上下文过多可能增加噪声。

但简单截取前两个文本块也会带来问题：

- 某些正确来源可能位于第 3 到第 5。
- 来源标题命中率可能下降。
- 多步骤问题可能需要多个文本块。

Day 28 的短上下文实验使来源命中率明显下降，所以最终回退。

结论不是“永远使用全部 Top-K”，而是：

上下文选择必须通过独立评估验证，不能只凭直觉缩短。


============================================================
三十二、为什么来源多样性也不能盲目强制
============================================================

多个高分文本块可能来自同一标题。

这既可能是冗余，也可能表示同一文档的多个段落都高度相关。

如果强制每个来源标题只能优先选择一次，可能把低相关的其他标题提前，并挤掉真正有用的相邻内容。

因此来源多样性是一种候选策略，不是天然正确的规则。

如果以后重新实现，应使用更大的独立数据集比较：

- 原始相似度顺序。
- 每个文档最多 N 块。
- Maximal Marginal Relevance。
- Cross-Encoder 重排序。
- 查询聚焦的上下文压缩。


============================================================
三十三、为什么评估过程需要固定生成参数
============================================================

generation.py 使用：

do_sample = False

这使生成过程采用确定性解码，减少随机采样造成的结果波动。

评估程序另外设置：

EVALUATION_MAX_NEW_TOKENS = 120

统一生成长度有助于公平比较不同代码版本。

但需要注意：

- 过小可能截断答案。
- 过大增加运行时间。
- 生成长度不是答案质量本身。


============================================================
三十四、为什么回答可能出现截断字符
============================================================

如果模型在最大 Token 数附近停止，答案可能不完整。

在某些终端显示中，还可能看到异常替代字符。

这通常需要区分：

- 模型生成被 max_new_tokens 截断。
- tokenizer 解码问题。
- Windows 终端编码问题。
- 文件本身的 UTF-8 编码问题。

py_compile 无法发现这些运行时问题。

必须实际运行并查看最终输出。


============================================================

============================================================
三十六、为什么程序化引用也需要测试
============================================================

引用逻辑虽然简单，但直接影响用户是否能追溯答案来源。

- 编号格式与正则表达式一致。
- 回答正文不被丢失。
- 标准拒答保持不变。
- 没有来源时不生成伪引用。

确定性逻辑最适合用单元测试保护。

============================================================
三十九、最终架构怎样保证引用可靠
============================================================

最终引用链路：

retrieve_chunks 返回排序后的真实文本块
→ build_rag_prompt 按相同顺序编号
→ generate_answer 生成正文
→ append_source_citations 按来源数量生成编号
→ sources 按相同顺序返回标题、chunk_id 和分数

只要三个位置使用相同 context_chunks 顺序：

- 提示词资料编号。
- 答案末尾引用编号。
- API sources 数组。

用户就可以把【资料N】映射回对应来源。


============================================================
四十、最终架构的失败保护
============================================================

当没有文本块通过门槛时：

- 不构造生成提示词。
- 不调用本地生成模型。
- 不追加任何引用。
- 返回标准拒答。
- sources 为空。

当存在通过门槛的文本块时：

- 模型只看到这些文本块。
- 回答后由程序追加合法范围内的编号。
- API 返回相同顺序的来源信息。

这比单纯在提示词中要求“不要幻觉”更可控。


============================================================
四十一、今天怎样正确理解 100% 指标
============================================================

以下指标为 100%：

- 门槛判断。
- 正确来源命中。
- 引用出现。
- 引用有效。
- 负例拒答。

它们只说明当前 9 个评估样例上的对应规则全部通过。

不能推导出：

- 所有未来问题都会正确。
- 引用来源中的每个句子都支持答案的每个结论。
- 模型完全不会幻觉。
- 0.48 永远是最佳门槛。
- 9 个样例能代表生产环境。


============================================================
四十二、引用出现、引用有效与引用忠实的区别
============================================================

引用出现：

答案里有资料编号。

引用有效：

编号在实际 sources 范围内。

引用忠实：

被引用资料真正支持答案中的具体结论。

Day 28 自动化实现了前两层。

第三层仍需要：

- 人工逐句检查。
- 更细粒度的句子到来源映射。
- Natural Language Inference 模型。
- LLM-as-a-Judge，并结合人工复核。


============================================================
四十三、为什么不能只看整体通过率
============================================================

如果整体通过率下降，可能原因完全不同：

- 无关问题被错误接受。
- 正确来源未进入 Top-K。
- 模型遗漏关键事实。
- 引用格式错误。
- 引用编号越界。
- 拒答内容不符合协议。

多维指标让每种失败可单独定位。

Day 28 的最终结果显示：

检索门槛、来源召回、引用与拒答已经稳定。

剩余改进重点是生成内容覆盖率。


============================================================
四十四、为什么评估报告要保存逐用例详情
============================================================

只保存汇总数字无法解释失败。

每个用例应至少记录：

- id。
- expected_passed。
- actual_passed。
- pass_match。
- expected_titles。
- source_title_hit。
- max_score。
- answer。
- answer_length。
- keyword_details。
- keyword_coverage。
- citation_numbers。
- citation_present。
- citation_valid。
- refusal_correct。
- case_success。
- sources。

这样可以从汇总指标继续下钻到具体故障。


============================================================
四十五、测试集、验证集和知识库要分开
============================================================

知识库保存系统可以检索的资料。

验证集用于：

- 选择门槛。
- 调整 Top-K。
- 修改提示词。
- 比较不同生成方案。

测试集用于：

- 参数确定后进行最终客观评估。

如果反复查看某个用例并为它修改代码，它实际上已经从测试集变成验证集。

因此 Day 28 最终没有继续针对唯一失败用例追求满分。

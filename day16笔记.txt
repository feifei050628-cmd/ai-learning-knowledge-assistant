二、RAG 的三个阶段

RAG 的全称是 Retrieval-Augmented Generation，中文通常称为“检索增强生成”。

1. Retrieval：检索

从外部知识库中寻找与用户问题相关的资料。

今天实现的检索过程：

用户问题
→ 查询向量
→ 与所有文档块向量计算相似度
→ Top-K
→ 最相关的 K 个文本块


2. Augmentation：增强

把检索到的资料加入大模型提示词，让模型在回答时能看到这些外部知识。

普通提示词：

用户问题 → 大模型

RAG 提示词：

用户问题
→ 检索相关资料
→ 资料 + 问题 + 回答规则
→ 大模型


3. Generation：生成

把增强后的提示词提交给生成式大模型，由大模型生成最终回答。

今天已经完成：

Retrieval：完成
Augmentation：完成
Generation：尚未接入生成式大模型

注意：构造出 rag_prompt 只是准备好了提示词字符串，并不代表大模型已经生成回答。


三、为什么要进行文档切块

长文档可能包含多个主题。如果直接把整篇文档转换成一个向量：

1. 多个段落的信息会混合在同一个向量中。
2. 与具体问题相关的局部信息可能被其他内容稀释。
3. 检索结果会带入大量无关内容。
4. 把整篇文档加入提示词会占用更多上下文长度。

因此通常先把长文档切成多个较短文本块，再为每个文本块分别生成向量。

今天使用的是固定字符长度切块。真实项目还可以按照：

段落、句号、标题、Markdown 层级、Token 数量

进行更自然的切块。


四、固定字符切块

核心函数：

def split_text(
    text: str,
    chunk_size: int = 45,
    overlap: int = 10,
) -> list[str]:
    if chunk_size <= 0:
        raise ValueError("chunk_size必须大于0")

    if overlap < 0 or overlap >= chunk_size:
        raise ValueError("overlap必须满足0 <= overlap < chunk_size")

    chunks = []
    start = 0

    while start < len(text):
        end = min(start + chunk_size, len(text))
        chunk = text[start:end].strip()

        if chunk:
            chunks.append(chunk)

        if end == len(text):
            break

        start = end - overlap

    return chunks


1. chunk_size

今天代码中的 chunk_size=45 表示每个文本块最多包含约 45 个 Python 字符。

这里的单位是字符，不是大模型 Token。


2. overlap

overlap=10 表示相邻文本块重复保留 10 个字符。

作用：减少一句话或重要知识点恰好在切块边界被截断造成的信息损失。


3. 为什么必须 overlap < chunk_size

下一次起点：

start = end - overlap

如果 overlap == chunk_size：

新的 start 与旧 start 相同，程序一直切同一段文本，造成死循环。

如果 overlap > chunk_size：

新的 start 会向后退，无法正常向文本末尾推进。

所以必须满足：

0 <= overlap < chunk_size


4. 为什么到末尾要 break

if end == len(text):
    break

表示当前文本块已经到达原文末尾。此时必须结束，否则继续用重叠长度计算起点，可能重复处理末尾内容。


五、文本块元数据

每个文本块不是只保存一段字符串，而是保存为字典：

{
    "chunk_id": "doc_001_chunk_1",
    "document_id": "doc_001",
    "title": "RAG基础",
    "text": "文本块正文",
}

字段作用：

document_id：确定文本块来自哪篇原始文档。
title：展示资料标题和来源。
chunk_id：区分同一篇文档里的不同文本块。
text：用于向量编码和加入提示词的正文。

document_chunks 的类型是：

list[dict]

保存来源信息可以用于：

1. 展示答案来源。
2. 让大模型标注引用。
3. 追踪检索结果对应的原始文档。
4. 排查向量与文本对应错误。


六、加载中文 BGE 向量模型

模型名称：

BAAI/bge-small-zh-v1.5

核心代码：

device = torch.device(
    "cuda" if torch.cuda.is_available() else "cpu"
)

model_id = "BAAI/bge-small-zh-v1.5"

tokenizer = AutoTokenizer.from_pretrained(model_id)
embedding_model = AutoModel.from_pretrained(model_id).to(device)
embedding_model.eval()


1. 为什么使用中文模型

今天检索的是中文知识库。中文模型更适合中文的分词方式和语义表示。

Day 15 使用的模型主要面向英文。大量中文文本直接使用英文模型，可能出现不合理分词和不准确的语义向量。


2. Tokenizer 与模型必须配套

AutoTokenizer 负责：

原始文本 → Token → Token ID

AutoModel 负责：

根据 Token ID 查询词向量并执行 Transformer 网络

二者必须使用相同 model_id，否则：

1. Token ID 与模型词表无法正确对应。
2. 相同编号可能代表不同 Token。
3. 模型会读取错误的词向量。

查询和文档也必须使用同一个向量模型，因为二者必须位于同一个语义向量空间。

即使两个不同模型都输出 512 维向量，也不能因此直接比较。


七、模型输入与输出形状

Tokenizer：

model_inputs = tokenizer(
    sample_texts,
    padding=True,
    truncation=True,
    max_length=64,
    return_tensors="pt",
)

padding=True：补齐到当前批次中最长文本的 Token 数量。
truncation=True：超过 max_length 时截断。
max_length=64：最多保留 64 个 Token。
return_tensors="pt"：返回 PyTorch Tensor。

注意：padding=True 不保证序列长度一定为 64。它只补齐到当前批次最长文本，64 是最大上限。


1. last_hidden_state

通用形状：

(batch_size, sequence_length, hidden_size)

如果形状为：

(4, 32, 512)

表示：

4：当前批次有 4 句话。
32：每句话补齐后有 32 个 Token 位置。
512：每个 Token 使用 512 维上下文向量表示。


2. 模型和输入必须在同一设备

model_inputs = {
    name: tensor.to(device)
    for name, tensor in model_inputs.items()
}

模型参数和输入 Tensor 要参与同一次数学计算，因此必须同时位于 CPU 或同时位于 GPU。


3. eval 与 no_grad

embedding_model.eval()

把模型切换到预测模式，使 Dropout 等训练和预测行为不同的层采用预测行为。

with torch.no_grad():

关闭梯度计算和计算图记录，减少内存、显存占用，提高推理效率。

eval() 不会自动关闭梯度，所以预测时通常二者一起使用。


八、CLS Pooling

BGE 官方推荐使用第一个 Token，也就是 CLS 位置的上下文向量作为句子向量：

sentence_embeddings = last_hidden_state[:, 0, :]

形状变化：

(batch_size, sequence_length, 512)
→ 取每句话第一个 Token
→ (batch_size, 512)

例如：

(4, 32, 512)
→ (4, 512)


为什么 Day 15 使用 Mean Pooling，而今天使用 CLS Pooling：

池化方法与具体模型的训练方式有关，应查看对应模型卡和推荐用法。

Day 15 的模型推荐 Masked Mean Pooling。
今天的 BGE 模型推荐 CLS Pooling。

不能认为所有 Transformer 都必须使用同一种池化方法。


九、L2 归一化

核心代码：

sentence_embeddings = F.normalize(
    sentence_embeddings,
    p=2,
    dim=1,
)

公式：

归一化向量 = 原向量 ÷ 原向量的 L2 模长

归一化结果：

1. 每个句子向量模长约等于 1。
2. 保留原向量方向。
3. 方便直接使用点积计算余弦相似度。

余弦相似度：

cos(A, B) = A·B ÷ (||A|| × ||B||)

归一化后：

||A|| = 1
||B|| = 1

所以：

cos(A, B) = A·B


十、文档切块与批量编码的区别

这是今天最容易混淆的知识点。

文档切块：

长文档 → 多个较短文本块

目的：避免多个主题混合，提高检索精度，减少无关上下文。

批量编码：

多个已经切好的文本块 → 分成多个 batch 送入模型

目的：控制内存和 GPU 显存占用。

所以：

“长文档主题多”是切块的原因。
“一次放入 GPU 会爆显存”是分批编码的原因。


十一、分批生成文档向量

函数签名：

def encode_passages(
    texts: list[str],
    batch_size: int = 8,
) -> torch.Tensor:

接收：

list[str]，也就是文本字符串列表。

返回：

torch.Tensor，形状为：

(文本数量, 512)

注意：它不返回 document_id、title 等元数据。元数据仍保存在 document_chunks 中。


1. 批次循环

for start in range(0, len(texts), batch_size):
    batch_texts = texts[start:start + batch_size]

range 三个参数：

0：从列表索引 0 开始。
len(texts)：文本列表中的文本数量。
batch_size：每次 start 增加的步长，也是每批最大文本数量。

如果有 10 个文本块，batch_size=4：

start 依次为 0、4、8。

第 1 批：4 个。
第 2 批：4 个。
第 3 批：2 个。


2. 每批结果形状

如果当前批次有 4 个文本：

last_hidden_state[:, 0, :] → (4, 512)

最后一批只有 2 个文本：

last_hidden_state[:, 0, :] → (2, 512)

所有批次拼接以后才得到：

(10, 512)


3. 为什么把结果移回 CPU

embedding_batches.append(batch_embeddings.cpu())

GPU 负责快速计算，生成后的文档向量移回 CPU 长期保存，可以释放显存，也方便保存到文件。


4. torch.cat

return torch.cat(embedding_batches, dim=0)

沿第 0 维，也就是文本数量维度拼接：

(4,512)
+ (4,512)
+ (2,512)
→ (10,512)


十二、最简单的内存向量索引

chunk_texts = [
    chunk["text"]
    for chunk in document_chunks
]

chunk_embeddings = encode_passages(
    chunk_texts,
    batch_size=4,
)

如果有 N 个文本块：

chunk_embeddings 形状为 (N, 512)

当前索引关系：

chunk_embeddings 第 0 行 ↔ document_chunks 第 0 项
chunk_embeddings 第 1 行 ↔ document_chunks 第 1 项
chunk_embeddings 第 i 行 ↔ document_chunks 第 i 项

顺序必须一直保持一致，否则向量检索结果会指向错误原文。

当前只是用 Tensor 保存向量，因此是最简单的内存向量索引。以后可以学习 FAISS 等专用向量索引。


十三、查询向量与检索指令

查询编码函数：

def encode_queries(queries: list[str]) -> torch.Tensor:

查询指令：

为这个句子生成表示以用于检索相关文章：

当前任务是：

短问题 → 检索较长资料

这属于非对称检索任务。BGE 推荐在查询前添加检索指令，文档块仍然按照原文编码。

查询向量和文档向量必须：

1. 使用同一个 Tokenizer。
2. 使用同一个模型。
3. 使用相同池化方法。
4. 使用相同归一化方法。

这样二者才位于相同的语义向量空间。


十四、批量计算相似度

查询只有 1 条：

query_embedding 形状为 (1, 512)

文档块有 N 条：

chunk_embeddings 形状为 (N, 512)

转置后：

chunk_embeddings.T 形状为 (512, N)

矩阵乘法：

(1,512) @ (512,N) → (1,N)

共同的 512 维句子特征被乘积求和，保留：

1 个查询 × N 个文本块

代码：

similarity_scores = (
    query_embedding
    @ chunk_embeddings.T
).squeeze(0)

squeeze(0)：

(1,N) → (N,)

消除大小为 1 的查询数量维度。


十五、Top-K 检索

top_scores, top_indices = torch.topk(
    similarity_scores,
    k=top_k,
)

torch.topk() 返回：

top_scores：最大的 K 个相似度。
top_indices：这些相似度对应的原始索引。

如果：

top_indices = tensor([5, 2, 7])

表示最相关的文本块依次是原列表中的第 5、2、7 项，不是新的排序位置。

取回原文：

index = index_tensor.item()
chunk = document_chunks[index]

item() 把单元素 Tensor 转换成普通 Python 整数或浮点数。


十六、余弦相似度不是概率

如果检索分数为：

0.8

不能解释为：

答案正确率 80%
内容有 80% 相同
岗位匹配率 80%
大模型回答概率 80%

它只表示两个归一化句子向量的方向比较接近，主要用于比较候选文本块的相对顺序。

是否相关的固定阈值需要使用真实业务数据进行评估和校准，不能直接把 0.5 或 0.8 当成通用标准。


十七、构造 RAG 检索上下文

retrieved_chunks 中每项保存：

rank：检索名次。
score：语义相似度数值。
chunk：完整文本块字典。

rank 用于给资料编号。
score 用于展示、比较和调试，不是由 score 自己完成排序；排序已经由 torch.topk() 的返回顺序确定。


1. 拼接资料

retrieved_context = "\n\n".join(context_parts)

join() 会把多个资料字符串连接成一个完整字符串，并在相邻资料之间插入两个换行符。

这样可以让不同资料拥有清晰边界。


2. 为什么保留资料编号和来源

[资料1]
来源：RAG基础
内容：……

作用：

1. 让大模型标注引用。
2. 展示回答依据。
3. 检查回答是否基于检索资料。
4. 排查检索是否返回错误文本块。


十八、RAG 提示词

提示词的核心规则：

1. 仅根据检索资料回答。
2. 资料不足时明确回答“现有资料不足”。
3. 不编造信息。
4. 标注使用了哪条资料。

完整结构：

回答角色与规则
→ 检索资料
→ 用户问题
→ 回答位置

提示词约束只能降低模型幻觉风险，不能保证大模型绝对不会产生幻觉。

day16_chunk_embeddings.pth 保存：

保存：

map_location="cpu"：把加载出的 Tensor 放到 CPU。

3. 为什么要保存 model_id

知识库向量由哪个模型生成，查询就必须继续使用同一个模型。

如果文档向量来自 BGE，但查询向量来自另一个模型，二者不在同一个向量空间，相似度没有可靠意义。


4. 一致性检查

if len(loaded_chunks) == loaded_embeddings.shape[0]:
    print("检查通过：文本块数量与向量行数一致")

必须保证：

loaded_chunks 第 i 项
↔ loaded_embeddings 第 i 行

数量不一致时，无法保证每个向量都能找到对应原文。


二十、为什么要持久化知识库

真实项目可能包含成千上万个文本块。为全部文本块运行预训练模型可能非常耗时。

如果每次启动程序都重新计算：

1. 重复占用 GPU。
2. 启动速度很慢。
3. 浪费计算资源。

保存以后：

程序启动
→ 加载 JSON 元数据
→ 加载 PTH 向量矩阵
→ 只为新查询生成向量
→ 执行 Top-K 检索

这样不需要重新计算所有文档向量。


二十一、26 道综合题标准答案

1. RAG 三阶段

Retrieval 从知识库检索资料；Augmentation 把资料加入提示词；Generation 让大模型根据问题和资料生成回答。

2. 为什么切块

整篇文档可能包含多个主题，整体向量会混合不同段落，降低检索精度，并占用更多大模型上下文长度。

3. chunk_size 与 overlap

今天的 chunk_size 是每块最大字符数；overlap 是相邻文本块重复保留的字符数。

4. overlap 限制

必须满足 0 <= overlap < chunk_size。相等会让起点不变并死循环，更大则会向后退。

5. 为什么保存来源字段

用于追踪来源、展示引用、区分文本块和排查错误。

6. 为什么使用中文 BGE

当前文档和问题是中文，中文模型更适合中文分词和语义表示。

7. 为什么 model_id 配套

Tokenizer 的 Token ID 必须与模型词表对应；查询与文档还必须处于同一个语义向量空间。

8. (4,32,512)

4 是句子数量，32 是每句 Token 数量，512 是每个 Token 的上下文向量维度。

9. CLS Pooling

last_hidden_state[:,0,:] 取每句话第一个 Token 的 512 维向量，结果为 (4,512)。

10. 为什么不能随意换池化

池化方式与模型训练方法有关，应按模型卡或推荐用法选择。BGE 推荐 CLS Pooling。

11. F.normalize

将每个句子向量的 L2 模长归一化为 1，保留方向，使归一化向量点积等于余弦相似度。

12. encode_passages 输入输出

接收 list[str]，返回形状为 (文本数量,512) 的 torch.Tensor。

13. 为什么分批

避免一次把大量数据放进 GPU 导致显存不足；每批计算完成后可移回 CPU。

14. 10 个文本、batch_size=4

共 3 批，数量分别为 4、4、2。

15. 20 个文本块

chunk_embeddings 形状为 (20,512)。

16. 为什么顺序一致

chunk_embeddings 第 i 行必须对应 document_chunks 第 i 项，否则会返回错误原文。

17. 相似度矩阵

(1,512) @ (8,512).T
= (1,512) @ (512,8)
= (1,8)

18. topk 返回值

返回 top_scores 和 top_indices；top_indices 是文本块在原向量矩阵中的行号。

19. 为什么只给查询加指令

当前是短问题检索较长文档的非对称检索任务，BGE 推荐给查询添加检索指令，文档按原文编码。

20. 相似度 0.8

只表示语义向量方向较接近，不是 80% 正确率、概率或岗位匹配率。

21. join

将多个资料字符串连接为一个字符串，在相邻资料之间插入两个换行符。

22. 为什么保存资料编号和来源

便于引用、展示依据、核对回答和排查检索错误。

23. rag_prompt 是否完成生成

没有。它只是字符串，还需要提交给生成式大模型才能得到回答。

24. JSON 与 PTH

JSON 保存文本块元数据；PTH 保存文本块向量矩阵。

25. 为什么保存 model_id

加载知识库后必须使用相同模型生成查询向量，保证查询和文档位于相同向量空间。

26. 完整流程

二十二、今天最容易混淆的知识点

1. 字符与 Token

今天 split_text() 使用字符串切片，所以 chunk_size 单位是字符。
Tokenizer 的 max_length 单位才是 Token。


2. 文档切块与批量编码

文档切块解决语义主题混合和上下文过长问题。
批量编码解决内存、显存占用问题。


3. CLS Pooling 与 Mean Pooling

没有一种池化方式适用于所有模型。应按具体模型训练方式和模型卡选择。


4. 相似度与概率

余弦相似度是向量几何关系，不是概率、正确率或完整业务匹配率。


5. rank 与 score

rank 是检索名次。
score 是语义相似度数值。
排序由 torch.topk() 的结果顺序完成，不是 score 字段自己排序。


6. 构造提示词与生成回答

rag_prompt 只是增强后的输入字符串。
只有把它提交给生成式大模型，才进入 Generation。


7. 相同维度与相同向量空间

两个模型都输出 512 维，不代表它们的向量可以比较。
查询和文档必须使用同一个模型和相同编码流程。

============================================================
二、为什么检索评估之后还要评估生成
============================================================

检索正确只能证明相关资料进入了 Pipeline，不能证明最终回答一定正确。

完整 RAG 链路：

用户问题
→ Retrieval 检索资料
→ Augmentation 构造增强提示词
→ Generation 生成自然语言回答
→ 返回回答与引用来源

即使 Retrieval 正确，后面的阶段仍可能发生问题：

1. 提示词没有清楚表达任务。
2. 模型忽略提示词中的限制。
3. 模型遗漏资料中的关键事实。
4. 模型增加资料之外的信息。
5. 模型没有按照要求输出引用。
6. max_new_tokens 太小导致回答被截断。
7. 原始文本块切分不完整，影响回答质量。

所以需要把最终回答作为独立对象进行评估。


============================================================
三、生成评估数据集
============================================================

generation_evaluation_cases.json 中，每个样例包含：

- id：稳定的样例编号。
- query：用户问题。
- expected_passed：预期是否通过相关性门槛。
- expected_title：预期来源标题；负例为 null。
- keyword_groups：答案应该覆盖的知识点。

正例示例：

{
  "id": "pytorch_training",
  "query": "PyTorch训练循环包括哪些主要步骤？",
  "expected_passed": true,
  "expected_title": "PyTorch训练",
  "keyword_groups": [
    ["前向传播"],
    ["损失"],
    ["清空梯度", "zero_grad"],
    ["反向传播", "backward"],
    ["更新参数", "step"]
  ]
}

负例示例：

{
  "id": "negative_cooking",
  "query": "番茄炒蛋应该怎么做？",
  "expected_passed": false,
  "expected_title": null,
  "keyword_groups": []
}


============================================================
四、关键词组的含义
============================================================

keyword_groups 中的每个内部列表代表一个知识点。同组关键词是“或者”关系，不同组之间是多个需要覆盖的知识点。

例如：

["清空梯度", "zero_grad"]

回答包含“清空梯度”或“zero_grad”中的任何一个，就算该组命中。

这样可以允许模型使用不同但可以接受的表达方式，避免只接受完全固定的答案文本。

关键词覆盖率：

命中的关键词组数量 / 关键词组总数

例如 4 组知识点命中 2 组：

2 / 4 = 0.5 = 50%


============================================================
五、check_keyword_groups 的工作过程
============================================================

函数首先执行：

normalized_answer = answer.lower()

这让 Token 和 token 等英文字母大小写差异不影响匹配。

随后逐组检查 alternatives，只要其中一个关键词出现在回答中，就记录：

- matched=true
- matched_keyword=实际命中的关键词

函数最终返回：

1. details：每组关键词的匹配详情。
2. coverage：总体关键词覆盖率。

详细结果有助于定位模型究竟遗漏了哪个知识点，而不仅仅看到一个总分。


============================================================
六、关键词覆盖率的能力与限制
============================================================

本次 4 个正例的关键词覆盖率全部为 100%，说明回答中出现了预期关键词。

但关键词出现不等于答案事实正确。

例如 Docker 回答中包含：

- 代码
- 依赖
- 运行环境
- 镜像

因此关键词覆盖率是 100%。但是模型还回答：

“这些组件在容器启动时会被复制到新的虚拟机上。”

知识库资料没有提供这项说法，而且容器不等同于新的虚拟机。关键词匹配没有发现这个问题。

因此关键词覆盖率只能作为规则型代理指标，它可以快速检查“是否提到必要内容”，不能证明：

- 句子逻辑正确。
- 事实完全来自资料。
- 否定关系正确。
- 回答没有幻觉。
- 回答整体语义准确。


============================================================
七、正确来源命中率
============================================================

正例通过以下代码检查期望标题：

source_title_hit = any(
    source["title"] == case["expected_title"]
    for source in result["sources"]
)

只要 sources 中至少有一个来源标题等于 expected_title，就算命中。

本次结果：

- RAG 问题命中“RAG基础”。
- Transformer 问题命中“Transformer基础”。
- PyTorch 问题命中“PyTorch训练”。
- Docker 问题命中“Docker部署”。

正确来源命中率为 4 / 4 = 100%。

这证明正确资料被返回，但不能单独证明生成模型正确使用了该资料。


============================================================
八、引用格式与正则表达式
============================================================

系统要求模型使用以下格式引用资料：

【资料1】
【资料2】

评估脚本使用：

CITATION_PATTERN = re.compile(r"【资料(\d+)】")

各部分含义：

- 【资料：匹配固定文本。
- (\d+)：捕获一个或多个数字。
- 】：匹配右方括号。

例如：

“答案来自【资料1】和【资料2】。”

extract_citations 会返回：

[1, 2]

正则表达式适合检查结构稳定、格式明确的文本模式。


============================================================
九、引用出现率与引用有效率
============================================================

引用出现率检查正例回答中是否至少出现一个【资料N】。

引用有效率进一步检查所有编号是否满足：

1 <= 引用编号 <= sources 数量

例如 sources 有 3 项：

- 【资料1】：有效。
- 【资料3】：有效。
- 【资料4】：无效。
- 没有任何引用：无效。

本次 4 个正例回答都没有输出【资料N】：

- citation_numbers=[]
- citation_present=false
- citation_valid=false

所以：

- 引用出现率：0 / 4 = 0%。
- 引用有效率：0 / 4 = 0%。

这说明提示词虽然要求引用，但 Qwen2.5-0.5B-Instruct 没有遵守输出格式。


============================================================
十、引用合法不等于引用正确
============================================================

当前 citations_are_valid 只检查编号范围。

如果模型输出【资料1】，并且 sources 中确实有资料1，编号就是合法的。但是当前规则没有检查：

- 引用位置附近的句子是否真的来自资料1。
- 资料1是否支持该项事实。
- 模型是否把资料1和资料2的内容混淆。
- 回答中的所有事实是否都有来源支持。

因此当前指标是“引用格式有效率”，不是严格的“事实忠实度”。


============================================================
十一、无关问题拒答评估
============================================================

负例的正确拒答必须同时满足：

1. result["passed"] is False。
2. answer.strip() == "现有资料不足"。
3. sources == []。

本次两个负例：

- “世界上最高的山峰是什么？”
- “番茄炒蛋应该怎么做？”

都没有通过 0.40 门槛，并返回：

- answer="现有资料不足"
- sources=[]

拒答准确率为 2 / 2 = 100%。

由于 RAGPipeline 在未通过门槛时提前 return，这两个负例没有调用生成模型，既降低了幻觉风险，也节省了推理时间。


============================================================
十二、case_success 的严格规则
============================================================

正例整体通过需要同时满足：

1. 门槛判断符合预期。
2. expected_title 出现在 sources 中。
3. 关键词覆盖率等于 100%。
4. 至少存在一个引用，并且引用编号有效。

负例整体通过需要：

1. 门槛判断符合预期。
2. 正确回答“现有资料不足”。
3. sources 为空。

本次 4 个正例前三项都通过，但全部缺少引用，所以 4 个正例的 case_success 都是 false。

两个负例正确拒答，所以 case_success 都是 true。

整体用例通过率：

2 / 6 = 0.3333 = 33.33%

这不是程序崩溃，而是严格评估规则成功发现了模型没有遵守引用要求。


============================================================
十三、为什么部分指标 100%，整体只有 33.33%
============================================================

本次指标并不矛盾：

- 门槛判断准确率 100%：6 个问题的接受或拒绝都正确。
- 来源命中率 100%：4 个正例都找到了正确标题。
- 关键词覆盖率 100%：4 个正例都包含要求的关键词。
- 拒答准确率 100%：2 个负例都正确拒答。
- 引用出现率和有效率 0%：正例都没有【资料N】。

case_success 使用“并且”规则。正例只要缺少引用，就不能整体通过。因此只有两个负例通过，总体为 33.33%。

多维指标比单一总分更有价值，因为它清楚告诉我们问题集中在“引用格式”，而不是检索、关键词或拒答。

============================================================
十五、切块质量会传递到生成阶段
============================================================

当前知识库使用简单切块，部分文本块在词语中间断开，例如：

- “加入提”与下一块的“，再把检索结果加入提示词”。
- “多个角度学”与下一块的“意力可以从多个角度学习”。
- “环境差”与下一块的“不同电脑之间的环境差异”。

这种切块会导致：

1. 单个文本块语义不完整。
2. 生成模型可能复制不完整句子。
3. 检索到一块时可能缺少后半句。
4. 提示词上下文可读性下降。
5. 关键词评估可能通过，但回答仍不自然。

因此生成质量问题不一定只由生成模型造成，也可能来自知识库预处理和切块方式。


============================================================
十六、max_new_tokens 与回答截断
============================================================

本次评估设置：

EVALUATION_MAX_NEW_TOKENS = 120

它限制最多生成 120 个新 Token，目的是缩短真实评估时间。

RAG 回答在句子中间结束，可能说明 120 个 Token 不足。需要注意：

- max_new_tokens 限制 Token 数，不是汉字数量。
- 回答提前遇到 EOS 时，也可能在达到上限前结束。
- 提高上限可以减少截断，但会增加生成时间和资源消耗。
- 上限过高也不能保证模型输出更准确。

正式判断截断原因时，可以记录实际生成 Token 数并检查是否达到上限。


============================================================
十七、为什么 Pipeline 只初始化一次
============================================================

main 中执行：

pipeline = RAGPipeline()

然后在循环中重复调用 evaluate_case。

这样 BGE、Qwen、tokenizer、知识库和向量只加载一次。若在每个 case 中重新创建 RAGPipeline，会导致：

- 模型反复加载。
- 评估时间大幅增加。
- 内存频繁分配和释放。
- 更容易发生资源不足。

这与 FastAPI lifespan 中只加载一次 Pipeline 的设计原则一致。


============================================================
十八、为什么在 main 中导入 RAGPipeline
============================================================

代码将导入放在 main 内：

def main():
    from rag_project.rag_pipeline import RAGPipeline

这样测试文件只导入 check_keyword_groups、extract_citations 等纯 Python 工具函数时，不需要实例化真实模型。

需要注意：导入模块本身通常不会执行 RAGPipeline()，但把真实 Pipeline 的使用限制在 main 中可以更清楚地分离：

- 快速、轻量的评估逻辑测试。
- 昂贵的真实端到端评估。


============================================================
十九、do_sample=False 的意义
============================================================

generation.py 中使用：

do_sample=False

这会减少随机采样，使相同模型、相同输入和相同环境下的输出更稳定。

对于离线评估，稳定输出有助于：

- 重复比较结果。
- 判断代码修改前后的差异。
- 降低随机性对指标的干扰。

确定性更强不代表回答一定正确，只表示重复运行更容易得到相同输出。

============================================================
二十二、规则评估与人工评审
============================================================

规则评估的优点：

- 速度快。
- 成本低。
- 结果稳定。
- 容易自动化。
- 失败原因比较直观。

规则评估的限制：

- 关键词出现不代表事实正确。
- 近义表达可能被错误判为缺失。
- 引用编号合法不代表引用支持事实。
- 无法充分判断逻辑、流畅度和幻觉。

因此完整生成评估通常需要结合：

1. 规则型指标。
2. 人工评审。
3. 更强模型作为评审器时的语义评估。
4. 对关键事实逐条进行来源一致性检查。

============================================================
二十五、Day 23 知识点总结
============================================================

1. 检索到正确资料不代表最终回答一定正确。
2. 完整 RAG 评估需要覆盖 Retrieval、Augmentation 和 Generation。
3. 评估集应该明确记录预期门槛状态、来源和关键知识点。
4. 同一关键词组中的词是可接受的替代表达。
5. 不同关键词组代表多个需要覆盖的知识点。
6. lower() 可以消除英文大小写对关键词匹配的影响。
7. 关键词覆盖率等于命中组数除以总组数。
8. 关键词覆盖率是规则型代理指标，不是真正的语义理解。
9. 关键词满分也可能包含资料之外的错误内容。
10. source_title_hit 检查期望标题是否存在于 sources。
11. 正则表达式适合提取格式固定的引用编号。
12. \d+ 表示一个或多个数字。
13. 引用出现率检查回答是否输出【资料N】。
14. 引用有效率检查编号是否处于 sources 范围内。
15. 空引用列表在当前规则中被判为无效。
16. 引用编号合法不代表引用内容真正支持答案。
17. 正确拒答要求 passed=false、固定拒答文本和空来源同时成立。
18. 负例在检索阶段提前返回，可以避免无依据生成并节省资源。
19. 正例 case_success 要求门槛、来源、关键词和引用全部通过。
20. 本次 4 个正例都缺少引用，因此全部没有整体通过。
21. 本次两个负例全部正确拒答。
22. 本次总体通过率为 2/6，即 33.33%。
23. 门槛准确率、来源命中率、关键词覆盖率和拒答准确率都是 100%。
24. 引用出现率和引用有效率都是 0%。
25. 多维指标可以准确定位失败集中在哪个环节。
26. 当前 Qwen 小模型没有遵守【资料N】引用要求。
27. Docker 回答出现了“新的虚拟机”这一潜在资料外内容。
28. 简单切块可能截断词语和句子，并把问题传递到生成阶段。
29. max_new_tokens 控制新生成 Token 上限，不等于汉字数量。
30. RAG 回答出现句尾截断，可能与 120 Token 上限有关。
31. Pipeline 应在循环外初始化一次，让全部样例复用模型。
32. 将真实 Pipeline 的使用放在 main 中，有助于保持辅助函数测试轻量。
33. do_sample=False 可以降低生成随机性，方便重复评估。
34. JSON 报告应同时保留汇总指标和逐样例结果。
35. 评估工具本身也需要 pytest 测试。
36. pytest.approx 或确定的数值断言可以验证指标计算。
37. pytest 通过只证明评估代码按预期工作，不证明模型质量优秀。
38. 规则评估速度快、可解释，但不能代替人工或语义评审。
39. Day 21 检查排名，Day 22 检查门槛，Day 23 检查完整回答。
40. 评估的价值不是强求满分，而是发现可以继续改进的具体问题。


============================================================
二十六、下一步可以改进什么
============================================================

根据本次报告，优先级较高的改进方向是：

1. 强化回答格式，让模型稳定输出【资料N】。
2. 对模型输出进行引用格式后处理或结构化生成。
3. 改进文本切块，尽量按照句子或段落边界切分。
4. 检查回答是否达到 max_new_tokens 上限。
5. 加入事实与来源一致性评估，发现 Docker 回答中的资料外内容。
6. 扩充生成评估集，加入更多表达方式和困难问题。
7. 将开发调试数据与最终测试数据分开。

不应该为了提高数字而直接删除引用指标。引用率为 0% 是一次有效发现，应推动系统改进。

二十九、Day 23 核心结论
============================================================

Day 23 把项目从“检索器能找到资料”推进到“完整回答可以被分维度、可重复地检查”。

完整评估链路：

读取生成评估数据
→ 初始化一次真实 RAG Pipeline
→ 检索问题并应用 0.40 门槛
→ 正例调用 Qwen 生成答案
→ 负例提前拒答
→ 检查来源标题
→ 检查关键词组
→ 提取并验证引用编号
→ 检查拒答结构
→ 计算多维指标
→ 保存逐样例报告
→ 使用 pytest 验证评估函数

本次最关键的发现是：检索、门槛、关键词和拒答都表现良好，但模型完全没有遵守引用格式，而且规则型关键词指标没有发现 Docker 回答中的资料外内容。这证明建立多维评估的意义不是获得一个漂亮总分，而是准确暴露系统下一步最值得改进的薄弱环节。

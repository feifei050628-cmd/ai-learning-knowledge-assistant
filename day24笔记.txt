二、新的知识库预处理流程
============================================================

今天建立的处理流程是：

原始 TXT/Markdown 文档
→ 统一换行和清理多余空白
→ 识别普通文本与 Markdown 代码块
→ 将普通文本拆成段落和句子
→ 按最大长度组合语义单元
→ 在相邻文本块之间保留重叠内容
→ 生成文档和文本块元数据
→ 保存 chunk_preview.json

这个流程位于向量化之前。它只负责决定“哪些文本将进入向量模型”，当前不会加载 BGE，也不会加载 Qwen。

当前正式检索仍然使用：

- day16_knowledge_base.json
- day16_chunk_embeddings.pth

因此 Day 24 的预处理改造不会立即替换或破坏现有 RAG API。


============================================================
三、为什么原始文档与处理结果要分开
============================================================

source_documents 保存人可以直接阅读和维护的原始资料，knowledge_base 保存程序处理后的文本块、向量和索引。

分开保存有几个好处：

1. 可以随时修改原始知识内容。
2. 修改切块参数后可以重新生成文本块。
3. 更换向量模型后可以重新生成 embedding。
4. 不需要手工维护大量 chunk_id。
5. 可以追踪每个检索结果来自哪个源文件。
6. 可以把生成文件与原始资料分别进行版本管理。

原始资料是“事实来源”，切块 JSON 和向量文件是“可以重新生成的派生产物”。

============================================================
六、normalize_text：文本标准化
============================================================

normalize_text 主要完成三件事：

1. 将 Windows 换行 \r\n 转换为 \n。
2. 将单独的 \r 也转换为 \n。
3. 删除每行末尾空白，并把三个以上连续换行压缩成两个。

核心过程：

text = text.replace("\r\n", "\n").replace("\r", "\n")
lines = [line.rstrip() for line in text.splitlines()]
text = "\n".join(lines).strip()
return re.sub(r"\n{3,}", "\n\n", text)

rstrip() 只删除行尾空白，不会主动删除行首缩进。最后的 strip() 会删除整篇文本最前面和最后面的空白。

统一文本格式的价值是：相同内容不会因为操作系统换行不同而产生不必要差异，后面的切块长度计算也更稳定。


============================================================
七、split_text_into_units：语义单元拆分
============================================================

切块程序没有直接每 500 个字符截断，而是先把文本转换为较小的语义单元。

普通文本处理顺序：

1. 按空行识别段落。
2. 清理段落中的多余换行和空白。
3. 使用中文和英文句末标点识别完整句子。

识别的主要标点包括：

- 。
- ！和 !
- ？和 ?
- ；和 ;

这样 chunk_text 可以把多个完整句子组合成文本块，而不是优先从句子中间截断。


============================================================
八、为什么要特殊处理 Markdown 代码块
============================================================

Markdown 使用三个反引号包围代码块。如果直接按照普通句号、换行或字符数切分，代码块可能失去开头、结尾、缩进或上下文。

split_text_into_units 先通过正则表达式识别完整代码块：

(```[\s\S]*?```)

其中：

- ``` 匹配代码围栏。
- [\s\S] 表示任意空白或非空白字符。
- *? 表示非贪婪匹配，遇到最近的结束围栏就停止。

识别出的代码块优先作为一个整体语义单元。只有代码块本身已经超过 chunk_size 时，才使用字符窗口后备切分。

测试中使用：

fence = "`" * 3

这是为了避免聊天界面把测试字符串中的三个反引号误认为外层代码展示结束。Python 运行时得到的内容仍是真正的 Markdown 代码围栏。


============================================================
九、chunk_size 的作用
============================================================

chunk_size=500 表示单个文本块最大约 500 个 Python 字符。

文本块过大可能导致：

1. 一个块中包含多个主题。
2. 检索结果不够精确。
3. 提示词占用更多 Token。
4. 生成模型更难找到重点。

文本块过小可能导致：

1. 完整定义或步骤被拆散。
2. 单个块缺少必要上下文。
3. 相似度依赖少量词语，结果不稳定。
4. 向量和元数据数量过多。

当前 500 是字符近似值，不是 Token 数。中文一个字符和模型 Token 并不严格一一对应。


============================================================
十、overlap 的作用
============================================================

overlap=80 表示希望下一块重复上一块末尾的一部分上下文。

假设一段重要定义正好位于两个文本块边界，如果完全没有重叠，前一块可能只有定义前半部分，后一块只有后半部分。加入重叠可以让后一块再次携带边界附近内容。

本项目的 select_overlap_units 优先复制完整语义单元，而不是机械截取最后 80 个字符。因此实际重叠长度可能小于 80。

这是“最大目标重叠”，不是保证精确重复 80 字符。

重叠过大也有代价：

1. 增加重复内容。
2. 增加 embedding 数量和存储。
3. 多个相似块可能同时占用 Top-K。
4. 降低检索结果的内容多样性。


============================================================
十一、超长语义单元的后备切分
============================================================

某些内容可能很长但没有标点，例如压缩文本、日志、长 URL、长代码或格式异常的文档。

如果单个语义单元已经超过 chunk_size，就无法继续依靠句子边界拆分。split_long_unit 此时使用滑动字符窗口：

start = 0
end = min(start + chunk_size, len(unit))
start = end - overlap

这种方式可以保证程序不会因为一个超长单元产生无限大的文本块，并且相邻窗口保留指定字符重叠。

字符窗口是后备方案，不是首选方案，因为它仍可能从词语或代码中间断开。


============================================================
十二、chunk_text 的工作过程
============================================================

chunk_text 的完整逻辑：

1. 检查 chunk_size 必须大于 0。
2. 检查 overlap 必须大于等于 0 且小于 chunk_size。
3. 调用 normalize_text 清洗文本。
4. 空文本直接返回空列表。
5. 调用 split_text_into_units 得到语义单元。
6. 超长语义单元交给 split_long_unit。
7. 逐个尝试把语义单元加入当前文本块。
8. 如果加入后没有超过 chunk_size，就继续累积。
9. 如果超过限制，就保存当前块。
10. 从当前块末尾选择完整语义单元作为重叠。
11. 开始构造下一个文本块。
12. 循环结束后保存最后一个块。
13. 避免重复加入完全相同的最后一块。

非法参数会抛出 ValueError，而不是产生不可信结果或陷入死循环。


============================================================
十三、稳定的 document_id
============================================================

create_document_id 使用文档相对路径生成编号：

1. 将反斜杠统一为正斜杠。
2. 转换为小写。
3. 使用 SHA-1 计算哈希。
4. 取前 10 位作为短编号。
5. 添加 doc_ 前缀。

例如：

doc_ba53fec8d7

这里使用 SHA-1 不是为了密码学安全，而是为了生成简短、可重复的标识符。

同一个相对路径重复处理时会得到相同 document_id。文件重命名或移动路径后，document_id 会发生变化。


============================================================
十四、read_document 的输出
============================================================

read_document 返回一个字典：

- document_id：稳定文档编号。
- source：相对源文件路径。
- title：文档标题。
- text：去除 Markdown 一级标题后的正文。
- char_count：正文字符数量。

如果文件内容为空，函数抛出 ValueError。这样可以在构建知识库时尽早发现空文件，而不是生成一个没有意义的向量。


============================================================
十五、load_documents 的工作过程
============================================================

load_documents 使用 rglob("*") 递归扫描 source_documents。

筛选条件：

1. path.is_file() 必须为文件。
2. 后缀必须属于 SUPPORTED_SUFFIXES。

路径经过 sorted 排序，因此相同目录结构下的处理顺序稳定。

如果原始文档目录不存在，或者目录中没有支持的文件，函数会抛出 FileNotFoundError。


============================================================
十六、build_chunks 与文本块元数据
============================================================

build_chunks 对每篇文档调用 chunk_text，并为每个结果加入：

- document_id
- source
- title
- chunk_id
- chunk_index
- text
- char_count

chunk_id 格式：

文档编号_chunk_四位序号

例如：

doc_ba53fec8d7_chunk_0001

四位序号让文本块排序和显示更整齐，也为以后同一文档产生大量文本块留出空间。

二十、pytest 临时目录权限问题
============================================================

test_document_metadata_is_stable 使用 pytest 的 tmp_path 创建临时 Markdown 文件。

第一次运行出现：

PermissionError: [WinError 5] 拒绝访问
C:\Users\21855\AppData\Local\Temp\pytest-of-21855

当时结果为：

6 passed, 1 error

这不是断言失败，也不是 document_id 算法错误，而是 pytest 无法访问 Windows 默认临时目录。

解决命令：

python -m pytest .\rag_project\tests\test_document_processor.py -v --basetemp=".pytest_tmp"

--basetemp 指定 pytest 使用项目中的临时目录。

.gitignore 中加入：

.pytest_tmp/

防止临时测试文件进入 Git。


============================================================
二十一、今天遇到的其他问题
============================================================

1. IndentationError

split_long_unit 中的 if end == len(unit) 曾经因为展示代码时多出缩进而触发 unexpected indent。修正原则是保证 if 与同一 while 内的 end、pieces.append、start 保持正确层级。

可以使用下面的命令先做纯语法检查：

python -m py_compile .\rag_project\document_processor.py

命令没有输出表示编译检查通过。

2. 运行模块没有输出

VS Code 文件标签存在白色圆点，表示文件尚未保存。终端执行的是磁盘中的旧版本，所以新添加的 main 没有运行。

解决方式：按 Ctrl+S，确认白点消失，再运行模块。

3. 聊天代码显示断断续续

测试字符串中的三个反引号与聊天界面的 Markdown 外层代码围栏冲突，导致界面提前结束代码块。后来改为运行时构造：

fence = "`" * 3

这只是展示层冲突，不是 Python 语法要求代码断开。

4. 说明文字被粘贴进 PowerShell

PowerShell 会把普通中文说明当成命令执行，并产生 CommandNotFoundException。终端中只应粘贴代码块里的命令，不要粘贴代码块外的解释文字。

============================================================
二十四、为什么今天不直接生成向量
============================================================

把预处理和向量化拆开有助于定位问题。

如果同时完成读取、切块、向量化和检索，而最终结果异常，就难以判断问题来自：

- 原始文档内容。
- 文本编码。
- 切块边界。
- 元数据。
- 向量模型。
- 向量文件顺序。
- 检索计算。

先生成 chunk_preview.json，可以在模型运行前低成本检查数据。当文本和元数据通过测试后，再生成向量，调试链路更加清晰。


============================================================
二十五、Day 24 知识点总结
============================================================

1. RAG 回答质量会受到知识库预处理质量影响。
2. 原始知识文档和派生知识库文件应分开保存。
3. source_documents 保存可维护的事实来源。
4. normalize_text 用于统一换行和清理多余空白。
5. 语义切块优先按照段落和完整句子切分。
6. 直接固定字符截断容易破坏词语和句子。
7. Markdown 代码块需要特殊识别并尽量完整保留。
8. chunk_size 控制单个文本块的最大字符数。
9. 字符数量不等于模型 Token 数量。
10. 文本块过大可能包含多个主题并降低检索精度。
11. 文本块过小可能失去必要上下文。
12. overlap 用于降低边界位置的信息丢失风险。
13. 本项目优先使用完整语义单元形成重叠。
14. 实际语义重叠长度可能小于配置上限。
15. 重叠过大会增加重复向量并占用 Top-K。
16. 无标点超长内容需要字符窗口作为后备方案。
17. 后备字符切分仍可能破坏语义，因此不是首选。
18. chunk_size 必须大于 0。
19. overlap 必须大于等于 0 且小于 chunk_size。
20. 非法参数应尽早抛出 ValueError。
21. document_id 标识原始文档。
22. chunk_id 标识文档中的具体文本块。
23. 稳定 ID 有利于追踪来源和比较不同版本。
24. 当前 ID 根据相对路径生成，移动文件会改变 ID。
25. SHA-1 在这里用于稳定标识，不用于密码安全。
26. source 保存源文件相对路径。
27. title 可以从 Markdown 一级标题提取。
28. chunk_index 表示文本块在文档中的顺序。
29. char_count 用于检查块长度和统计知识库规模。
30. sorted 可以让文件处理顺序更稳定。
31. 空文件应该在构建知识库时被拒绝。
32. ensure_ascii=False 让 JSON 中文保持可读。
33. indent=2 让 JSON 便于人工检查。
34. chunk_preview.json 不包含 embedding。
35. 预览文件目前不会替换正式检索知识库。
36. 当前 4 篇文档较短，所以每篇只有一个块。
37. 单元测试可以用较小 chunk_size 验证多块切分。
38. pytest tmp_path 可以创建隔离的临时测试文件。
39. PermissionError 与断言失败属于不同类型的问题。
40. --basetemp 可以改变 pytest 临时目录。
41. .pytest_tmp 应加入 .gitignore。
42. py_compile 可以在运行功能前检查 Python 语法。
43. VS Code 标签白点表示文件没有保存。
44. 聊天中的 Markdown 围栏可能与测试字符串中的反引号冲突。
45. 预处理、向量化和检索应分层实现和验证。

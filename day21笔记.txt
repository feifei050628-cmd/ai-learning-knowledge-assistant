============================================================
二、软件测试与模型评估的区别
============================================================

Day 20 的 pytest 主要回答：

“程序是否按照规定工作？”

例如：

- 非法 top_k 是否返回 422。
- Pipeline 未加载是否返回 503。
- Pipeline 异常是否转换成 500。
- response_model 是否过滤多余字段。
- query 是否清除首尾空白。

Day 21 的真实检索评估主要回答：

“检索模型找到的资料是否正确？”

例如：

- RAG 问题是否检索到“RAG基础”。
- Transformer 问题是否检索到“Transformer基础”。
- Docker 问题是否检索到“Docker部署”。
- 与知识库无关的问题是否被相关性门槛拒绝。

二者不能互相替代：

- 软件测试通过，不代表模型检索质量好。
- 检索指标高，不代表 API 的状态码、异常处理和参数校验正确。
- 一个可靠项目需要同时进行软件测试与模型质量评估。


============================================================
三、评估数据集 evaluation_cases.json
============================================================

评估数据集包含 12 个带有预期结果的样例。

每个样例包含：

- id：稳定且唯一的样例编号。
- query：提交给检索器的问题。
- expected_title：期望检索到的资料标题；无关问题使用 null。

正例示例：

{
  "id": "rag_process",
  "query": "RAG由哪三个阶段组成？",
  "expected_title": "RAG基础"
}

负例示例：

{
  "id": "negative_weather",
  "query": "北京今天的天气怎么样？",
  "expected_title": null
}

当前数据分布：

- 8 个正例：RAG基础、Transformer基础、PyTorch训练、Docker部署各 2 个问题。
- 4 个负例：山峰、做菜、天气和股票问题。

正例用于检查系统能不能找到知识库中的相关资料；负例用于检查系统会不会对知识库之外的问题误判为相关。


============================================================
四、为什么评估数据必须包含正例和负例
============================================================

如果只评估正例，降低 min_similarity 往往可以让更多问题通过，但系统也可能错误接受大量无关问题。

如果只评估负例，提高 min_similarity 往往可以拒绝更多无关问题，但系统也可能拒绝本来能够回答的相关问题。

因此门槛存在权衡：

- 门槛过低：召回较多，但误接受无关问题的风险上升。
- 门槛过高：拒绝更严格，但可能漏掉相关问题。

同时包含正例和负例，才能观察接受相关问题与拒绝无关问题之间的平衡。


============================================================
五、真实检索评估的执行链路
============================================================

运行命令：

python -m rag_project.evaluate_retrieval

完整流程：

读取 evaluation_cases.json
→ 加载知识库文本块和向量矩阵
→ 加载真实 BGE tokenizer 和检索模型
→ 逐个读取 query
→ 添加 BGE 检索指令
→ tokenizer 编码
→ 模型生成查询向量
→ 对查询向量进行 L2 归一化
→ 查询向量与知识库向量矩阵相乘
→ torch.topk 取得最相似的 3 个文本块
→ 查找 expected_title 的排名
→ 单独使用 0.40 判断是否接受
→ 统计各项指标
→ 保存 retrieval_evaluation_report.json

这个过程加载了真实检索模型，但没有加载 Qwen 生成模型，因为 Day 21 只评估 Retrieval，不评估 Generation。


============================================================
六、为什么评估时传入 min_similarity=-1.0
============================================================

evaluate_retrieval.py 调用 retrieve_chunks 时使用：

min_similarity=-1.0

这样做是为了先取得完整 Top-K 排名，不让业务门槛提前把 retrieved_chunks 清空。

检索评估需要分开观察两个问题：

1. 排名是否正确：正确资料有没有进入 Top-K，排在第几名。
2. 门槛是否正确：最高相似度是否应该被系统接受。

由于归一化向量的余弦相似度理论范围是 -1 到 1，设置 -1.0 可以让检索函数返回 Top-K。随后评估脚本再独立计算：

accepted = max_score >= min_similarity

这里的 min_similarity 才是实际配置中的 0.40。

需要注意：-1.0 只是评估时获取排名的技术手段，不是把线上业务门槛改成 -1.0。


============================================================
七、find_expected_rank 的作用
============================================================

find_expected_rank 会遍历 retrieved_chunks，并从 1 开始记录排名：

for rank, chunk in enumerate(retrieved_chunks, start=1):
    if chunk["title"] == expected_title:
        return rank

可能结果：

- 返回 1：正确资料排第 1。
- 返回 2：正确资料排第 2。
- 返回 3：正确资料排第 3。
- 返回 None：正确资料没有进入 Top 3。

使用 start=1 是因为人类通常把最佳结果称为第 1 名，而不是第 0 名。


============================================================
八、Hit@3
============================================================

Hit@3 检查正确资料是否出现在前 3 个检索结果中。

公式：

Hit@3 = 正确资料进入 Top 3 的正例数量 / 正例总数

本次结果：

8 / 8 = 1.0 = 100%

Hit@3 只关心“有没有进入前 3”，不区分正确资料排第 1、第 2 还是第 3。

因此以下三个结果对 Hit@3 都算命中：

- 正确资料排名 1。
- 正确资料排名 2。
- 正确资料排名 3。


============================================================
九、MRR@3
============================================================

MRR 是 Mean Reciprocal Rank，即平均倒数排名。

单个正例的倒数排名：

- 正确资料第 1 名：1 / 1 = 1.0
- 正确资料第 2 名：1 / 2 = 0.5
- 正确资料第 3 名：1 / 3 ≈ 0.333
- 没进入 Top 3：0

公式：

MRR@3 = 所有正例倒数排名之和 / 正例总数

本次 8 个正例的正确资料都排第 1，因此：

(1 + 1 + 1 + 1 + 1 + 1 + 1 + 1) / 8 = 1.0

Hit@3 相同的两个系统，MRR@3 更高的系统通常把正确资料排得更靠前。


============================================================
十、相关问题接受率
============================================================

相关问题接受率检查正例的最高相似度是否通过门槛。

公式：

相关问题接受率 = 被门槛接受的正例数量 / 正例总数

本次结果：

8 / 8 = 100%

它只说明相关问题通过了门槛。要确认资料本身是否正确，还需要结合 Hit@3 或 expected_rank。


============================================================
十一、无关问题拒绝率
============================================================

无关问题拒绝率检查负例是否被门槛正确拒绝。

公式：

无关问题拒绝率 = 被门槛拒绝的负例数量 / 负例总数

本次结果：

4 / 4 = 100%

如果无关问题通过门槛，RAG 可能把不相关资料交给生成模型，增加错误回答和幻觉风险。


============================================================
十二、总体正确率
============================================================

当前脚本对正例和负例使用不同判断规则。

正例正确要求：

- expected_title 进入 Top 3；并且
- 最高相似度通过 0.40 门槛。

负例正确要求：

- 最高相似度没有通过 0.40 门槛。

公式：

总体正确率 = 判断正确的全部样例数量 / 全部样例数量

本次结果：

12 / 12 = 100%


============================================================
十三、相似度分数不等于概率
============================================================

当前查询向量和知识库向量都进行了 L2 归一化，因此矩阵乘积可作为余弦相似度使用。

相似度越高，表示查询向量和文本块向量的方向越接近。但 0.70 不能理解成“70% 概率正确”。

相似度分数会受到以下因素影响：

- 检索模型。
- 查询指令。
- 知识库内容。
- 文本切块方式。
- 问题表达方式。
- 向量归一化方法。

因此 min_similarity 不应凭感觉解释为概率，而应使用具有代表性的评估数据进行校准。


============================================================
十四、本次门槛 0.40 的实际表现
============================================================

本次正例的最高相似度范围：

- 最低正例：0.4430，问题为“RAG由哪三个阶段组成？”
- 最高正例：0.7866，问题为“PyTorch训练循环包括哪些步骤？”

本次负例的最高相似度范围：

- 最低负例：0.2442
- 最高负例：0.3705，问题为“现在应该购买哪只股票？”

当前门槛：0.4000

在这 12 个样例中：

- 所有正例分数都高于 0.40。
- 所有负例分数都低于 0.40。
- 最低正例 0.4430 与最高负例 0.3705 之间相差约 0.0725。

这说明 0.40 在当前小数据集上形成了清晰分界，但分数间隔不算很大。增加更难的近义问题、模糊问题和领域相近负例后，分界可能发生变化。


============================================================
十五、safe_divide 的作用
============================================================

safe_divide 在分母为 0 时返回 0.0：

def safe_divide(numerator, denominator):
    if denominator == 0:
        return 0.0
    return numerator / denominator

它可以避免评估集暂时没有正例或没有负例时发生 ZeroDivisionError。

不过从评估设计角度看，如果正例或负例为 0，相应指标缺乏意义。正式评估应保证两类样例都存在，而不能只依靠 safe_divide 隐藏数据集问题。


============================================================
十六、评估报告 retrieval_evaluation_report.json
============================================================

报告包含三个主要部分：

1. settings：评估配置和样本数量。
2. metrics：汇总指标。
3. cases：每个样例的详细结果。

每个 case 记录：

- id
- query
- expected_title
- retrieved_titles
- expected_rank
- max_score
- accepted
- correct

保存详细结果非常重要，因为汇总指标只能说明“总体表现”，详细记录才能帮助定位具体失败样例。

例如指标下降时，可以判断问题属于：

- 正确资料没有进入 Top-K。
- 正确资料进入 Top-K，但排名靠后。
- 相关问题被门槛错误拒绝。
- 无关问题被门槛错误接受。


============================================================
十七、生成 JSON 报告时的编码设置
============================================================

保存报告使用：

json.dump(
    report,
    file,
    ensure_ascii=False,
    indent=2,
)

其中：

- encoding="utf-8"：文件使用 UTF-8 编码。
- ensure_ascii=False：中文直接保存，不转换成 \uXXXX。
- indent=2：使用两空格缩进，便于人工阅读和 Git 对比。


============================================================
十八、如何读取报告
============================================================

PowerShell 命令：

$report = Get-Content `
    ".\rag_project\retrieval_evaluation_report.json" `
    -Raw `
    -Encoding UTF8 |
    ConvertFrom-Json

$report.settings | Format-List
$report.metrics | Format-List

含义：

- Get-Content：读取文件。
- -Raw：把整个文件读取成一个字符串，而不是多行字符串数组。
- -Encoding UTF8：按 UTF-8 解码中文。
- ConvertFrom-Json：把 JSON 字符串转换为 PowerShell 对象。
- $report.settings：访问配置部分。
- $report.metrics：访问指标部分。
- Format-List：用列表形式显示对象字段。

查看错误样例可使用：

$report.cases |
    Where-Object { -not $_.correct } |
    Select-Object `
        id, `
        query, `
        expected_title, `
        retrieved_titles, `
        expected_rank, `
        max_score, `
        accepted |
    Format-List

本次所有 correct 都是 true，因此该命令不会输出错误样例。

============================================================
二十、100% 指标不代表生产可用
============================================================

本次五项指标都是 100%，但不能得出“系统在任何问题上都能达到 100%”的结论。

原因包括：

1. 总样本只有 12 个。
2. 正例只有 8 个，负例只有 4 个。
3. 问题由开发者人工设计，表达方式比较清晰。
4. 知识库只有少量主题和文本块。
5. 多个问题与资料标题和正文的语义距离较近。
6. 负例与知识库主题差异明显，属于较容易拒绝的负例。
7. 没有覆盖错别字、简称、口语、省略和多意图问题。
8. 没有覆盖与知识库主题接近但实际无法回答的困难负例。
9. 没有评估生成答案是否忠实、完整和无幻觉。
10. 没有评估大规模知识库下的速度、内存和并发。

因此本次结果应称为“小规模基线评估结果”，而不是生产质量证明。


============================================================
二十一、如何改进评估数据集
============================================================

后续可以逐步加入：

1. 同一个问题的多种表达方式。
2. 带错别字或中英文混合的问题。
3. 需要区分相近主题的问题。
4. 与知识库主题相关但文档没有答案的困难负例。
5. 很短、很长或信息不完整的问题。
6. 同时包含多个意图的问题。
7. 容易把两个文档混淆的问题。
8. 来自真实用户日志并经过隐私处理的问题。

评估样例应有明确、可复查的标签。模糊样例最好由多人检查，避免错误标签使指标失真。


============================================================
二十二、门槛校准应注意数据泄漏
============================================================

如果反复查看同一组评估结果并调整 min_similarity，最终门槛会特别适合这 12 个样例，但不一定适合新问题。这属于对评估集过拟合。

更规范的做法是拆分数据：

- 开发集：用于观察错误并选择门槛。
- 测试集：门槛确定后只用于最终评估。

不能在同一份数据上不断调参，再把这份数据的最高结果当成系统对未知问题的真实性能。

二十五、面试表达

二十七、Day 21 核心结论
============================================================

Day 21 将项目从“真实检索看起来可以工作”升级为“真实检索可以通过固定数据和指标重复评估”。

最终质量检查链路：

评估数据集
→ 加载真实知识库与 BGE
→ 为每个问题生成查询向量
→ 计算相似度并取得 Top 3
→ 检查正确资料排名
→ 使用 0.40 判断接受或拒绝
→ 计算五项指标
→ 保存逐样例 JSON 报告
→ 运行 pytest 检查软件回归

当前 12 个基线样例全部正确，说明检索排名和 0.40 门槛在这组数据上表现良好。下一步的重点不是盲目庆祝 100%，而是逐步扩大数据集、加入更困难的问题，并用独立数据进行门槛校准和生成质量评估。

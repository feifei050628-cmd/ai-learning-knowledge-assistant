============================================================
四、什么是文本向量 Embedding
============================================================

计算机不能直接理解“RAG 是什么”这类自然语言的语义。

Embedding 模型会把一段文本转换成一组数字，例如：

[0.013, -0.042, 0.087, ...]

这些数字共同表示文本的语义位置。

含义相近的文本，向量方向通常也比较接近。

含义无关的文本，向量方向通常相差较大。

因此，检索过程不是直接比较两个字符串是否相同，而是：

1. 把知识库文本块转换成向量。
2. 把用户问题转换成向量。
3. 计算问题向量与所有文本块向量的相似度。
4. 选出相似度最高的文本块。

Embedding 不是对文本进行加密，也不是生成答案。

它的任务是把语义映射到一个可以计算距离或相似度的数字空间。


============================================================
五、为什么向量维度是 512
============================================================

向量维度由检索模型决定。

当前使用：

BAAI/bge-small-zh-v1.5

这个模型为每段文本输出 512 维向量。

因此：

- 1 个文本块对应形状为 (512,) 的向量。
- 2 个文本块对应形状为 (2, 512) 的矩阵。
- 810 个文本块对应形状为 (810, 512) 的矩阵。

维度越大不一定代表检索一定越好。

模型质量、训练数据、文本语言、切块策略和评估样本同样重要。

知识库向量和用户问题向量必须使用同一个检索模型生成。

如果知识库使用 BGE 生成，而问题使用其他模型生成，它们不位于同一个向量空间，相似度就没有可靠意义。

============================================================
七、为什么要先加载并校验切块预览
============================================================

向量生成比较耗时，不能拿到任何 JSON 就直接开始计算。

构建器首先读取：

expanded_chunk_preview.json

然后检查：

1. 顶层结构是否正确。
2. 是否存在 chunks 列表。
3. 预览中声明的 chunk_count 是否与实际数量一致。
4. 每个文本块是否包含必需字段。
5. chunk_id 是否为空。
6. chunk_id 是否重复。
7. text 是否为空。
8. 文本块顺序是否能够稳定保存。

必需字段包括类似：

- document_id
- title
- source
- chunk_id
- chunk_index
- text
- char_count
- category
- day

具体字段以项目中的 REQUIRED_CHUNK_FIELDS 为准。

校验的核心目的不是追求形式，而是防止“元数据和向量静默错位”。

如果某个块缺少 ID，后续无法稳定引用来源。

如果 chunk_id 重复，不同向量可能被错误地认为来自同一个文本块。

如果预览声明有 810 块，实际却只有 809 块，说明上游数据可能损坏或生成没有完成。


============================================================
八、为什么文本块顺序非常重要
============================================================

正式知识库由两个文件共同组成：

1. JSON 元数据。
2. PTH 向量矩阵。

它们依靠列表行号建立对应关系。

例如：

metadata[0] 对应 embeddings[0]
metadata[1] 对应 embeddings[1]
metadata[809] 对应 embeddings[809]

检索得到第 35 行相似度最高时，程序会读取 metadata[35]，从而获得该块的标题、来源和文本。

如果元数据排序发生变化，但向量没有按相同顺序重新生成，就会出现严重错误：

相似度属于 A 文本，但返回的来源却显示 B 文本。

这种错误未必会抛异常，所以比普通语法错误更危险。

因此构建时必须保证：

- 元数据与向量在同一次构建中产生。
- 二者的数量完全一致。
- 二者的顺序完全一致。
- 不手工单独重排 JSON。


============================================================
九、tokenizer 在做什么
============================================================

模型不能直接接收 Python 字符串。

tokenizer 会把文本转换成 token ID，并构造模型需要的张量。

典型调用会设置：

padding=True
truncation=True
max_length=模型允许的最大长度
return_tensors="pt"

padding=True：

同一个批次中的文本长度不同，较短文本会补齐，使它们形成规则矩阵。

truncation=True：

文本超过模型最大 token 长度时进行截断，避免模型输入超限。

return_tensors="pt"：

让 tokenizer 返回 PyTorch 张量。

注意：

字符数不等于 token 数。

Day 24 的 chunk_size=500 是字符级切块规则，模型的 max_length 是 token 级输入限制，两者不是同一个概念。


============================================================
十、为什么要把模型输入移动到 DEVICE
============================================================

项目根据环境选择：

DEVICE = torch.device(
    "cuda" if torch.cuda.is_available() else "cpu"
)

如果模型在 GPU 上，输入张量也必须在 GPU 上。

如果模型在 CPU 上，输入张量也必须在 CPU 上。

模型和输入不在同一个设备时，会出现设备不一致错误。

常见处理方式：

inputs = {
    name: tensor.to(DEVICE)
    for name, tensor in inputs.items()
}

截图中正式构建时显示：

运行设备：cuda

说明模型推理使用了可用 GPU。

保存前把最终向量移回 CPU，可以让向量文件更通用，之后即使在没有 GPU 的环境也能加载。


============================================================
十一、为什么使用 torch.inference_mode()
============================================================

构建知识库只做模型推理，不训练模型。

训练时需要保存梯度和中间计算图，以便反向传播。

推理时不需要这些信息。

使用：

with torch.inference_mode():
    outputs = model(**inputs)

主要作用：

1. 不记录梯度。
2. 减少显存或内存占用。
3. 降低额外计算开销。
4. 明确表达这段代码只用于推理。

这和 model.eval() 作用不同但通常配合使用。

model.eval() 会让 Dropout、BatchNorm 等层进入推理行为。

torch.inference_mode() 负责关闭梯度相关机制。


============================================================
十二、为什么取 last_hidden_state[:, 0]
============================================================

模型输出的 last_hidden_state 通常形状为：

(batch_size, sequence_length, hidden_size)

三个维度分别代表：

1. 当前批次有多少段文本。
2. 每段文本有多少个 token 位置。
3. 每个 token 的隐藏向量维度。

代码：

outputs.last_hidden_state[:, 0]

含义：

- 第一个冒号：选择批次中的全部文本。
- 0：选择每段文本第 0 个 token 的表示。
- 隐藏维度默认全部保留。

因此结果形状从：

(batch_size, sequence_length, 512)

变为：

(batch_size, 512)

第 0 个位置通常是 CLS 位置，用来作为整段文本的聚合表示。

不同 embedding 模型可能要求 CLS pooling、mean pooling 或专用接口，不能把同一写法机械套用到所有模型。

当前项目根据 BGE 模型的使用方式取 CLS 表示。


============================================================
十三、为什么要做 L2 归一化
============================================================

代码核心：

F.normalize(embeddings, p=2, dim=1)

p=2 表示使用 L2 范数。

dim=1 表示对每一行向量分别归一化。

归一化后，每个向量的长度接近 1：

||v||₂ = 1

截图中的抽样结果：

向量长度：[1.0, 1.0]

归一化带来的重要性质：

当两个向量的 L2 长度都是 1 时，它们的点积等于余弦相似度。

cos(a, b) = a · b / (||a|| × ||b||)

因为：

||a|| = 1
||b|| = 1

所以：

cos(a, b) = a · b

这样检索时可以通过矩阵乘法高效计算问题与全部文本块的相似度。

注意：

知识库向量和问题向量必须采用相同的归一化规则。


============================================================
十四、为什么使用批量向量化
============================================================

如果一次只处理一个文本块，需要频繁调用 tokenizer 和模型，效率较低。

如果一次把 810 个文本块全部送入 GPU，可能消耗过多显存。

小批量是二者之间的平衡。

当前配置：

EMBEDDING_BATCH_SIZE = 16

意味着大多数批次包含 16 个文本块，最后一个批次可以少于 16 个。

批量流程：

chunks[0:16]
chunks[16:32]
chunks[32:48]
...
最后一个不足 16 的批次

每一批得到形状类似：

(16, 512)

最后使用：

torch.cat(batch_embeddings, dim=0)

沿第 0 维拼接为：

(810, 512)

批次大小不是模型质量参数，它主要影响：

- 运行速度
- GPU 显存占用
- CPU 内存占用

显存不足时可以减小批次大小。

设备性能较好时可以尝试增大，但必须重新验证稳定性。


============================================================
十五、encode_chunk_batch() 的职责
============================================================

这个函数只处理一个批次。

职责可以概括为：

文本列表
→ tokenizer
→ 输入移动到 DEVICE
→ 模型推理
→ 提取 CLS
→ L2 归一化
→ 移回 CPU
→ 返回二维向量张量

把单批逻辑独立成函数的好处：

1. 职责清楚。
2. 容易使用假 tokenizer 和假 model 做单元测试。
3. 批次循环不必重复底层推理代码。
4. 出错时更容易定位是在单批编码还是整体拼接。


============================================================
十六、encode_all_chunks() 的职责
============================================================

这个函数负责组织全部文本块的批量处理。

主要步骤：

1. 检查 batch_size 是否大于 0。
2. 按 batch_size 对 chunks 切片。
3. 提取当前批次中的 text。
4. 调用 encode_chunk_batch()。
5. 保存每一批的结果。
6. 输出构建进度。
7. 使用 torch.cat() 合并所有批次。
8. 检查最终行数是否等于 chunk 数量。
9. 检查所有数值是否有限。
10. 返回完整向量矩阵。

最终进度显示：

向量生成进度：810/810

这表示所有 810 个文本块都已经完成向量化。


============================================================
十七、为什么检查 NaN 和 Infinity
============================================================

正常向量应该由有限浮点数组成。

异常数值包括：

- NaN：不是一个有效数字。
- +Infinity：正无穷。
- -Infinity：负无穷。

如果这些数值进入相似度计算，排序结果可能失效。

可以使用类似：

torch.isfinite(embeddings).all()

检查所有元素是否为有限数。

这是一种“构建时失败”的设计：

发现索引损坏就立即停止，不把问题留到用户查询时才暴露。


============================================================
十八、正式元数据 JSON 保存什么
============================================================

day26_knowledge_base.json 不只是纯文本块列表，还保存知识库版本和构建信息。

实际版本：

day26-knowledge-base-v1

来源预览版本：

day25-expanded-preview-v1

重要内容通常包括：

- 知识库版本
- 上游预览版本
- 检索模型 ID
- 向量维度
- 文档统计
- 文本块统计
- 文本块列表
- 每块的标题、来源、文本和 ID

JSON 的优势：

1. 人工可以直接查看。
2. 方便排查来源和文本。
3. 可以被不同语言读取。
4. 适合保存结构化元数据。

JSON 不适合高效保存大型浮点矩阵，因此向量单独保存为 PTH。


============================================================
十九、PTH 向量文件保存什么
============================================================

day26_chunk_embeddings.pth 保存完整 PyTorch 张量。

实际张量形状：

(810, 512)

每一行对应一个文本块的 512 维向量。

保存：

torch.save(embeddings, path)

加载时应考虑：

torch.load(
    path,
    map_location="cpu",
    weights_only=True,
)

map_location="cpu" 的作用：

无论文件最初在哪个设备生成，都先加载到 CPU，增强兼容性并避免意外占用 GPU。

weights_only=True 的作用：

限制加载范围，适合只需要张量数据的场景，降低加载不可信 pickle 对象的风险。

原则：

不要随意加载来源不明的 .pth 文件。


============================================================
二十、为什么保存前把向量移到 CPU
============================================================

模型可以在 CUDA 上运行，但保存文件最好包含 CPU 张量。

原因：

1. 没有 GPU 的电脑也能加载。
2. 加载时不依赖原来的 GPU 编号。
3. 更适合作为可搬运的索引产物。
4. 查询程序可以根据需要再把张量移动到目标设备。

因此单批编码结束时会把结果转换为 CPU 张量。

截图中“运行设备：cuda”和“向量所在设备：cpu”同时出现是合理的：

- cuda 表示模型推理发生在 GPU。
- cpu 表示返回和保存的向量已经移回 CPU。


============================================================
二十一、为什么构建时要检查向量长度
============================================================

代码会抽样计算：

vector_norms = sample_embeddings.norm(p=2, dim=1)

正常结果应接近：

[1.0, 1.0, ...]

如果长度明显不接近 1，可能说明：

1. 忘记做 L2 归一化。
2. 归一化维度写错。
3. 取错了模型输出。
4. 数据中出现异常值。

归一化验证不是检索质量评估。

它只能证明向量生成过程符合预期的数学格式，不能证明检索一定准确。


============================================================
二十二、旧 main() 导致只输出两个向量的问题
============================================================

阶段开发时先写了一个“小批量冒烟测试 main()”。

它只取前两个文本块，用来确认：

- 模型能否加载
- tokenizer 能否工作
- 输出形状是否为 (2, 512)
- 向量是否归一化

后来已经写好完整构建函数，但如果文件底部仍然保留旧 main()，执行：

python -m rag_project.knowledge_base_builder

就只会看到：

向量矩阵形状：torch.Size([2, 512])

而不会生成 810 个向量，也不会保存正式文件。

解决方法是把旧 main() 替换为正式流程：

1. load_chunk_preview()
2. validate_chunks()
3. load_retrieval_components()
4. encode_all_chunks()
5. 检查向量长度
6. save_knowledge_base()

如何判断当前执行的是正式 main()：

- 能看到从 16/810 持续增长的进度。
- 最终显示 810/810。
- 输出正式知识库生成完成。
- 输出元数据和向量文件路径。


============================================================
二十三、为什么 py_compile 通过仍可能运行失败
============================================================

命令：

python -m py_compile ".\rag_project\knowledge_base_builder.py"

只检查 Python 语法是否正确。

它可以发现：

- 缩进错误
- 括号不完整
- 字符串未闭合
- 其他语法错误

它不能发现所有运行时问题，例如：

- 名称没有定义
- 文件不存在
- JSON 结构不正确
- 模型加载失败
- GPU 显存不足

============================================================
二十四、测试中为什么使用 FakeTokenizer 和 FakeModel
============================================================

单元测试的目标是验证项目代码逻辑，而不是反复下载和运行真实大模型。

FakeTokenizer 模拟 tokenizer：

- 接收文本列表。
- 记录输入。
- 返回形状可控的张量。

FakeModel 模拟模型：

- 接收 tokenizer 输出。
- 返回可预测的 last_hidden_state。
- 不需要下载模型。
- 不需要 GPU。

SimpleNamespace 可以快速构造带有 last_hidden_state 属性的假输出对象。

这样能够验证：

1. 是否取了第 0 个 token。
2. 输出是否为二维矩阵。
3. 每个向量是否归一化。
4. 文本是否按批次提交。
5. 多批结果是否正确拼接。

这类测试运行快、结果稳定，也不会受到网络和模型缓存影响。

二十六、tmp_path 和 monkeypatch 的意义
============================================================

tmp_path 是 pytest 提供的临时目录。

测试保存文件时使用 tmp_path，可以避免覆盖正式知识库。

monkeypatch 用来临时替换模块中的变量、路径或函数。

例如可以把正式输出路径临时指向测试目录。

测试结束后替换会自动恢复。

这样做可以：

1. 避免测试污染真实文件。
2. 让每个测试相互独立。
3. 在没有网络和大模型的情况下测试流程。
4. 提高测试的可重复性。

============================================================

warning 不等于测试失败。

当前结果表示：

- 没有失败用例。
- 没有错误用例。
- 有一个未来需要关注的依赖兼容提醒。

后续可以升级或调整相关依赖解决提醒，但不应把 warning 当作当前功能失败。

============================================================
三十一、top_k 中可能混入低相关文本块的问题
============================================================

当前检索逻辑需要重点继续验证：

如果最高分文本块通过门槛，passed 会变为 true。

随后 top_k 可能返回多个文本块。

其中第 1 个文本块很相关，但第 2、3 个文本块的分数可能明显较低。

如果所有 top_k 块都直接交给生成模型，低相关内容可能造成：

- 上下文噪声增加
- 回答偏题
- 引用来源不够准确
- 生成模型混合多个不相关知识点

因此后续评估不能只看 max_score，还应检查：

- 每个返回块的分数
- 每个块是否达到独立门槛
- top_k 应固定还是动态变化
- 是否需要同时满足排名与最低分数条件

这一点是扩大知识库后非常重要的质量控制问题。

============================================================
三十七、常见问题排查
============================================================

问题 1：只能看到 (2, 512)。

原因：仍在运行阶段用的小批量冒烟测试 main()。

处理：确认 main() 调用 encode_all_chunks() 和 save_knowledge_base()。

问题 2：NameError，某个函数没有定义。

原因：调用了没有导入、没有定义或名称拼写错误的函数。

处理：从 Traceback 最后一行向上看实际出错文件和行号。

问题 3：ImportError，config 中找不到常量。

原因：配置尚未保存、名称拼写不一致，或导入了旧模块状态。

处理：保存 config.py，核对常量名，然后重新启动命令。

问题 4：CUDA out of memory。

原因：批次过大或 GPU 同时被其他程序占用。

处理：减小 EMBEDDING_BATCH_SIZE，关闭不需要的 GPU 任务后重试。

问题 5：模型和输入设备不一致。

原因：模型在 CUDA，输入还在 CPU，或相反。

处理：确保 tokenizer 返回的每个张量都移动到 DEVICE。

问题 6：向量行数不等于文本块数。

原因：批次遗漏、空批次、拼接维度错误或上游数据变化。

处理：检查循环切片、进度最后值和 torch.cat(dim=0)。

问题 7：retrieval 打印很长的正文。

原因：它在展示命中的学习笔记文本块，不一定是异常。

处理：查找 Traceback、score、title、source 等结构化输出。

问题 8：新增笔记后检索不到。

原因：只新增了原始文件，没有重新生成预览和向量，或 API 没有重启。

处理：依次运行 note_importer、knowledge_base_builder，并重启 API。

============================================================
四十、今天必须掌握的知识点总结
============================================================

1. Embedding 把文本语义转换成可计算的向量。
2. 当前 BGE 模型输出 512 维文本向量。
3. 810 个文本块组成 (810, 512) 向量矩阵。
4. tokenizer 把字符串变成模型可接收的 token 张量。
5. padding 用于批次对齐，truncation 防止输入超长。
6. 模型和输入张量必须位于同一个设备。
7. model.eval() 设置推理行为，inference_mode() 关闭梯度开销。
8. last_hidden_state[:, 0] 取得每段文本的 CLS 表示。
9. L2 归一化让每个向量长度接近 1。
10. 归一化后点积等于余弦相似度。
11. 小批量编码兼顾速度和显存占用。
12. torch.cat(..., dim=0) 合并所有文本块向量。
13. 构建前必须校验文本块结构和唯一 ID。
14. 元数据第 i 项必须对应向量第 i 行。
15. JSON 保存可读元数据，PTH 保存张量。
16. 保存 CPU 张量提高跨设备加载兼容性。
17. map_location="cpu" 控制加载位置。
18. weights_only=True 更适合只加载张量的安全场景。
19. FakeTokenizer 和 FakeModel 让模型相关逻辑可以快速单测。
20. tmp_path 和 monkeypatch 防止测试污染正式文件。
21. py_compile 通过只代表语法正确，不代表运行逻辑正确。
22. 59 passed 表示全部测试通过，warning 不等于失败。
23. retrieval.py 通过统一配置名切换到新知识库。
24. 新增学习笔记后必须重新生成预览、重新向量化并重启 API。
25. 当前是手动全量重建，不是自动或增量更新。
26. .pth 被 Git 忽略，GitHub 使用者需要本地重建向量。
27. 知识库扩大后必须重新评估检索质量和相似度门槛。
28. 不能只看最高分，还要检查 top_k 中每个文本块的相关性。
